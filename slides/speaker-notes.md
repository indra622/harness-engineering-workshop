장면과 질문 (예시 초안): AI교양 글 한 편의 작업이 끝났다. 사용자가 원문을 보냈고, 최종본이 확정됐고, 삽화를 만들어 보관했고, 비공개 초안을 만든 뒤 다시 열어 확인했다. 질문: 이 흐름이 단계를 건너뛰지 않게 하는 것은 누구일까?

이 장면은 개념 설명용이다. 실제 화면, 계정 정보, 공개 발행은 보여 주지 않는다. 참가자는 실습하지 않는다. 듣고 질문만 한다. 낯선 라벨 몇 개는 나중에 설명한다.

학습 목표는 다음과 같다.

1. 모델, 에이전트, 런타임, 하네스, 오케스트레이션, 도구, 스킬, 플러그인, 커넥터, MCP, 프롬프트, 컨텍스트, 토큰, 컨텍스트 창, 메모리, 세션, 워커, 서브에이전트, 워크플로우, 자동화, 완료 보고, 검증, 로컬 실행, 클라우드 실행, 리모트 컨트롤을 각각 설명할 수 있다.
2. 같은 모델이라도 컨텍스트, 도구, 검증 기준이 다르면 결과의 재현성과 점검 가능성이 달라질 수 있음을 설명할 수 있다. 결과가 반드시 좋아진다고 말하지 않는다.
3. 완료 보고와 검증 증거를 구분하고, 결정적으로 확인할 수 있는 검증 항목을 만들 수 있다.
4. 로컬 실행, 클라우드 실행, 리모트 컨트롤을 서로 다른 축으로 설명하고, 구성 요소별로 위치를 말할 수 있다.
5. 업무용 하네스의 구성 요소, 즉 명세, 루브릭, 기록, 절차, 사람의 교정과 상황별 페르소나 선택이 어떻게 맞물리는지 실제 사례로 설명할 수 있다.

장면과 질문 (예시 초안): 개념이 먼저인가, 사례가 먼저인가? 질문: 이 워크샵을 들은 뒤 AI교양 흐름을 용어로 다시 읽을 수 있을까?

오늘은 개념과 사례를 번갈아 본다. 먼저 실행 틀의 기본 네 개념을 익히고, 방금 익힌 개념을 OpenClaw 구조에서 찾는다. 쉬는 시간 뒤에는 세션, 워커, 서브에이전트를 배우고, 마지막에 다섯 사례를 한 흐름으로 되짚는다. 아직 배우지 않은 용어는 사례에서 미리 정의하지 않고, 이름만 보여 준 뒤 해당 슬라이드에서 다룬다고 약속한다.

2.1 설명용 가상 CSV

아래 CSV는 용어를 설명하기 위한 가상 자료다. 실제 고객 정보가 없고, 참가자가 만들거나 열어 볼 파일이 아니다.

```
ticket_id,received_at,channel,category,summary,priority,assignee,status,resolved_at
T-1001,2026-10-03 09:12,email,결제,카드 중복 청구 문의,high,담당A,open,
T-1002,10/3/2026,chat,,배송지 변경 요청,긴급!!,,closed,2026-10-04
T-1002,10/3/2026,chat,,배송지 변경 요청,긴급!!,,closed,2026-10-04
```

- 행 식별자는 파일 안의 줄 번호와 ticket_id를 함께 쓴다. 헤더는 1행이므로 위 발췌의 첫 번째 데이터 행은 "2행 T-1001"이다.
- 원본 행 수와 고유 티켓 수를 따로 센다. 위 발췌는 데이터 행 3개, 고유 ticket_id 2개다.
- 날짜가 두 가지 이상으로 읽히면 임의로 바꾸지 않는다. 예를 들어 03/04/2026은 3월 4일일 수도 4월 3일일 수도 있으므로 모호 목록에 적는다.

2.2 설명에서 쓰는 확인 기준

- 보고서 건수는 원본 행 수와 고유 티켓 수를 구분해 적는다.
- 모호한 행은 빠짐없이 목록으로 적는다. 값이 없는 칸은 추정하지 않고 미확인으로 표시한다.
- 주요 주장마다 행 식별자를 인용한다. 중복 ticket_id만으로 행을 합치지 않는다.

2.3 AI교양 제작 흐름 (S21, S27, S28 공통 사례)

이 흐름은 실제 AI교양 제작 세션의 기록을 교육용으로 정리한 것이다. 이번 작업으로 제작을 실행하지 않는다. 최종 확정은 사람이 하는 전환 조건이며, 이 게이트는 그대로 유지한다.

1. 사용자가 원문을 보내면 받은 본문을 v01로 보존하고 정리 노트와 인덱스에 연결한다. 수정본이 오면 새 버전을 만들고 이전 버전은 남긴다.
2. 세션에서 문장과 논지를 다듬고, 필요하면 근거를 확인한다.
3. 사용자가 최종본을 명시적으로 확정한다. 확정 전에는 제작 단계를 열지 않는다.
4. 확정 뒤에는 삽화 한 장을 만들고, 확정 문장과 이미지를 Obsidian에 보존하고, 설정된 광고와 안내 이미지를 넣은 네이버 비공개 초안을 만든다.
5. 초안을 다시 열어 본문, 대표 이미지, 순서, 카테고리를 확인한다. 공개 발행은 이 흐름에 포함되지 않는다.

2.4 참가자 전제

- 참가자는 실습을 하지 않는다. 설치, 로그인, 파일 준비, API 키 발급을 요구하지 않는다.
- OpenClaw, Remote, 플러그인, MCP 서버를 참가자 노트북에 설치하지 않는다.
- 시연은 강사가 한다. 시연 자료는 아직 만들지 않았다.

S3. 모델 (5분부터 8분까지, 3분)

장면과 질문 (예시 초안): 팀장이 AI에게 '내일 회의 준비해 줘'라고 한 줄만 보낸다. 안건과 참석자는 적지 않았다. 질문: 안건을 모르는데도 그럴듯한 준비안이 나올까?

한 문장 정의: 모델은 입력된 텍스트와 맥락을 받아 다음 출력을 생성하는 학습된 계산 장치이며, 그 출력에는 답변 텍스트와 도구 호출 요청이 포함될 수 있다.

상세 설명:
- 모델은 실행 중에 파일을 열거나 명령을 실행하지 않는다. 입력을 받아 출력을 계산해 내보낸다.
- 도구가 필요하면 "이 도구를 이 인자로 호출해 달라"는 구조화된 요청을 출력한다. 실제 호출은 런타임이 한다(S5).
- 같은 모델이라도 입력과 설정이 다르면 출력이 달라진다. 모델 이름이 결과 전체를 정하지는 않는다.

장면에 다시 적용 (예시 초안): 같은 한 줄을 보내면 나오는 것은 일반적인 회의 준비 목록이다. 입력: '내일 회의 준비해 줘'. 출력: 추측이 섞인 일반 목록. 안건 세 줄을 덧붙여 다시 보내면 출력의 주제가 안건 쪽으로 바뀐다.

강사용 보충 예시 (화면 생략): "tickets.csv에 몇 행이 있는가"라는 질문에서 CSV 내용이 입력에 들어 있어야 모델이 그 내용을 근거로 답할 수 있다. 경로만 주고 내용을 넣지 않으면 모델은 파일을 보지 못하고 그럴듯한 숫자를 추측할 수 있다.

헷갈리는 지점: 모델과 에이전트는 다르다. 모델은 출력을 만들고, 에이전트는 그 출력이 도구 실행과 결과 확인으로 이어져 여러 단계를 도는 구성이다(S4).

화면 구성: 첫 화면은 장면과 질문만 보인다. 답을 공개한 뒤 정의와 적용을 보인다. 입력 상자(프롬프트 한 줄과 CSV 발췌 세 줄), 모델 상자, 출력 상자 두 개를 가로로 배치한다. 출력 상자 하나는 텍스트 답변, 다른 하나는 read_file(path=tickets.csv) 요청이다. 모델 상자 옆에 "여기서는 파일이 열리지 않는다"는 주석을 단다.

확인 질문과 모범 답안: 모델이 "tickets.csv를 읽겠다"고 요청했다. 파일은 이미 읽힌 것인가? 아니다. 요청만 나온 것이며, 런타임이 도구를 실행해 결과를 돌려준 뒤에야 파일 내용이 입력에 들어간다.

시간: 5분부터 8분까지, 3분. 장면 도입 20초에서 30초와 예측 질문 5초에서 10초를 포함한다.

S4. 에이전트 (8분부터 11분까지, 3분)

장면과 질문 (예시 초안): 일정 안내 메일의 초안을 AI에게 맡긴다. 일정 정보가 빠지면 되물어 채우고 고쳐 쓴다. 발송은 하지 않는다. 질문: 초안을 쓰고, 빠진 정보를 확인하고, 고치는 일을 끝나는 조건이 있는 반복으로 돌리면 에이전트에 가까울까?

한 문장 정의: 에이전트는 목표를 받아 모델의 판단, 도구 실행, 결과 확인을 반복하며, 종료 조건이 충족될 때까지 작업을 이어 가는 실행 구성이다.

상세 설명:
- 핵심은 반복 루프다. 모델이 다음 행동을 고르고, 도구 결과를 보고, 다시 다음 행동을 고른다. 필요하면 다음 행동을 선택해 실행을 이어갈 수 있는 구조가 핵심이다. 실제 응답 횟수만으로 에이전트 여부를 판정하지 않는다.
- 루프를 끝내는 조건이 있어야 한다. 예를 들어 "보고서가 저장되고 체크리스트 항목이 모두 통과하면 종료"다.
- 한 실행 주체가 여러 단계를 도는 것도 에이전트 구성이다. 여러 에이전트가 있어야 하는 것은 아니다.

장면에 다시 적용 (예시 초안): 메일 장면에서 목표는 '초안 완성, 발송 금지, 빠진 일정 확인 후 종료'다. 입력: 목표와 일정 메모. 출력: 초안 한 개와 확인 필요 항목 목록. 발송은 이 반복에 넣지 않는다.

강사용 보충 예시 (화면 생략): 목표는 "tickets.csv로 보고서를 쓰고 가상의 경로 output/report.md에 저장하라. 체크리스트를 통과하면 끝낸다"이다. 행동은 CSV 열기, 행 수 세기, 빈 칸 목록 만들기, 보고서 쓰기, 체크리스트 대조 순서다. 실패 항목이 있으면 보고서 쓰기로 돌아간다.

헷갈리는 지점: 에이전트와 모델은 다르다(S3). 에이전트와 서브에이전트도 다르다. 서브에이전트는 에이전트 안에서 나온 하위 실행이며, 모든 에이전트가 가지는 것은 아니다(S25).

화면 구성: 첫 화면은 장면과 질문만 보인다. 답을 공개한 뒤 정의와 적용을 보인다. 원형 루프. 노드는 목표와 종료 기준, 모델 판단, 도구 실행, 결과 확인, 종료 조건 판단이다. 종료 조건에서 "아니오"는 모델 판단으로, "예"는 종료로 간다. 루프 밖에 목표 문장과 종료 기준 문장을 적는다.

확인 질문과 모범 답안: 모델이 보고서를 한 번 쓰고 끝났다. 에이전트인가? 한 번에 끝났다는 사실만으로는 판단할 수 없다. 도구 결과를 보고 후속 행동이나 종료를 정할 수 있는 실행 구조인지 확인해야 한다.

시간: 8분부터 11분까지, 3분. 장면 도입 20초에서 30초와 예측 질문 5초에서 10초를 포함한다.

[제작 브리프]
S4. 에이전트 (8분부터 11분까지, 3분)

화면 핵심 문장: 목표, 행동, 결과 확인, 종료 조건이 도는 구성이다.

레이아웃과 도식: 상단에 목표를 고정하고 원형 루프 네 노드(모델 판단, 도구 실행, 결과 확인, 종료 조건)를 둔다. 발송은 루프 밖 회색 점선.

공개 순서와 진행: 장면 20초, 질문 '쓰고 확인하고 고치는 순환이면 에이전트에 가까울까?' 5초에서 10초. 루프를 그린 뒤 메일 목표를 채운다.

발표자 노트: v10 S4 정의, 루프, 종료 조건, 서브에이전트와 구분. 메일은 초안만, 발송 없음. 응답 횟수만으로 에이전트 여부를 판단하지 않는다. 도구 결과에 따라 후속 행동과 종료를 정할 수 있는 구조인지 본다.

필요 자료와 준비 상태: AS-03 과정 루프.

제작 검수 포인트: 발송이 루프 밖에 있는가. 여러 에이전트가 필요하다는 인상이 없는가.

## S5. 런타임

원본 v10 S5. 런타임
시간: 11분부터 14분까지, 3분
출처: docs/plans/slide-content-plan-v10.md S5, docs/production/slide-production-brief-v01.md S5

[v10 원문]
S5. 런타임 (11분부터 14분까지, 3분)

장면과 질문 (예시 초안): '지난주 회의 메모 파일 열어 줘'라는 요청을 보낸다. 실제로 파일을 여는 쪽은 누구일까? 질문: AI 모델이 파일을 직접 열까?

한 문장 정의: 런타임은 모델의 도구 호출 요청을 받아 권한을 확인한 뒤 도구를 실행하고, 결과를 다시 모델 입력으로 돌려주며 다음 호출을 이어 주는 실행 계층이다.

상세 설명:
- 모델은 요청만 만든다. 런타임이 요청이 등록된 도구인지, 실행 권한이 있는지 확인한 뒤 실행을 연결한다.
- 실행 결과, 즉 파일 내용, 오류 메시지, 종료 코드를 정리해 다음 모델 호출의 입력에 넣는다. 이 되돌림이 루프를 가능하게 한다.
- 도구가 내 기기에서 도는지 외부 서버에서 도는지는 런타임 구성에 따라 달라진다(S31, S32).
- 여기서 말하는 런타임은 Python이나 Node.js 같은 언어 실행 환경과 다르다. 런타임 전체를 하네스라고 부르지도 않는다(S6).

장면에 다시 적용 (예시 초안): 입력: 파일 열기 요청. 모델 출력: read_file(path=meeting-memo) 요청 한 줄. 런타임이 권한을 확인해 파일을 열고 내용을 다음 입력에 넣는다. 권한이 없으면 오류가 돌아온다.

강사용 보충 예시 (화면 생략): 모델이 read_file(path=tickets.csv)를 요청한다. 런타임이 등록된 파일 읽기 도구를 실제 권한 설정에 따라 실행해 결과를 모델 입력에 넣는다. 예시 폴더만 다루라는 문서 지시가 기술적 접근 차단을 자동으로 만드는 것은 아니다. 파일이 없었다면 "파일 없음" 오류가 돌아가고, 모델은 그 오류를 보고 다음 행동을 고른다.

헷갈리는 지점: 모델은 판단과 생성을 맡고, 런타임은 실행을 연결한다. 하네스는 컨텍스트, 도구, 상태, 검증까지 포함하는 더 넓은 틀이다(S6). 명명 경계는 제품마다 다를 수 있다.

화면 구성: 첫 화면은 장면과 질문만 보인다. 답을 공개한 뒤 정의와 적용을 보인다. 순서도. 모델 요청 → 런타임(권한 확인, 도구 실행) → 파일 읽기 도구 → 결과 → 런타임(결과 정리) → 모델 입력 → 모델 다음 판단. 모델과 런타임 상자는 테두리 색을 다르게 하고, "파일은 런타임 쪽에서만 열린다"는 주석을 단다.

확인 질문과 모범 답안: 모델이 파일 읽기를 요청했는데 접근이 차단됐다. 답변 내용만 보면 되는가? 아니다. 권한 기록과 도구 오류 결과를 함께 봐야 한다. 답변이 그럴듯해도 실행 결과가 없을 수 있다.

시간: 11분부터 14분까지, 3분. 장면 도입 20초에서 30초와 예측 질문 5초에서 10초를 포함한다.

[제작 브리프]
S5. 런타임 (11분부터 14분까지, 3분)

화면 핵심 문장: 모델은 요청만 만들고, 런타임이 실행해 결과를 돌려준다.

레이아웃과 도식: 상단 모델(read_file 요청 한 줄), 가운데 런타임 띠(권한 확인, 실행), 하단 파일. 결과 화살표가 위로 돌아온다.

한 문장 정의: 하네스는 모델이 안정적으로 일하도록 컨텍스트, 도구와 실행 위치, 상태 저장, 검증 절차를 묶은 작업 틀 전체다. 이 워크샵은 이 정의를 쓰며, 제품마다 범위가 다를 수 있다.

상세 설명:
- 컨텍스트 구성: 어떤 지침과 입력 파일을 모델에 넣을지 정한다. 예를 들어 규칙 파일과 tickets.csv를 명시적으로 읽힌다.
- 도구와 실행 위치, 상태와 검증: 어떤 도구를 쓸지, 결과 버전과 인계 파일을 어디에 남길지, 완료를 무엇으로 판단할지 정한다.
- 하네스를 바꾸는 것과 모델을 교체하거나 재학습하는 것은 별개다. 같은 모델이라도 틀이 다르면 재현성과 점검 가능성이 달라진다. 결과가 반드시 좋아진다는 보장은 없다.

장면에 다시 적용 (예시 초안): 문서 검토 장면에서 입력은 문서와 체크리스트, 출력은 검토 메모다. 하네스는 체크리스트를 읽히는 지침, 검토 메모를 저장할 위치, 빠진 항목을 다시 확인하는 절차까지 함께 정한다.

강사용 보충 예시 (화면 생략): Claude Code나 Codex는 한 줄 요청을 받는 경우에도 기본 하네스가 있다. 이 예시는 하네스가 없는 실행과 있는 실행의 비교가 아니라, 기본 실행에 업무용 구성을 얼마나 더했는지의 비교다. 보강된 가상 예시는 같은 CSV에 규칙 파일, 출력 형식 파일, 체크리스트를 명시적으로 읽히고, 결과를 별도 경로에 저장하며, 인계 파일을 남긴다. CEO Agent 사례(S26)도 같은 구조를 업무용 명세와 기록으로 채운 것이다.

헷갈리는 지점: 하네스와 오케스트레이션은 다르다. 하네스는 틀이고, 오케스트레이션은 그 안에서 순서와 역할을 배정하는 일이다(S8). 하네스와 런타임도 다르다. 런타임은 실행을 연결하는 층이다.

확인 질문과 모범 답안: 검증 체크리스트 파일은 하네스의 어느 칸에 속하는가? 검증 칸이다. 완료 판단 기준을 담기 때문이다. 상태 칸은 진행 기록을 담는다.

- 로컬 운영 문서의 기준이며, 실시간 상태는 이번 작업에서 확인하지 않았다.

구체 예시: 디스코드에서 "보고서 검증해 줘"라는 요청이 오면 게이트웨이가 세션을 만들고 코디네이터가 직접 확인할지 워커에 맡길지 정한다. 워커가 파일을 고치면 부모가 테스트와 파일 상태를 독립적으로 확인한 뒤 답장한다. 이 흐름은 가상 예시이며 실제 요청 기록이 아니다.

헷갈리는 지점: 게이트웨이는 채널과 세션을 관리하는 층이고, 코디네이터는 맡길지 판단하는 주체다. 워커는 배정된 실제 작업을 수행하며 쓰기를 맡은 경우 작성 책임을 진다(S24). 원격 앱은 리모트 컨트롤 화면이다(S33).

한 문장 정의: 도구는 모델이 요청하고 런타임이 실행하는, 이름과 입력 형식과 결과 형식이 정해진 호출 가능한 기능이다.

장면에 다시 적용 (예시 초안): 입력: list_files(folder=meetings, sort=date). 출력: 파일 이름 목록. 메모는 어떤 순서로 찾을지 적을 뿐 아무것도 실행하지 않는다.

헷갈리는 지점: 도구는 절차가 아니다. "날짜를 ISO 형식으로 바꾼다"는 절차이고, 그 변환을 실행하는 함수 호출이 도구다. 도구와 MCP도 다르다. MCP는 도구를 연결하는 통신 규약이다(S14).

화면 구성: 첫 화면은 장면과 질문만 보인다. 답을 공개한 뒤 정의와 적용을 보인다. 도구 카드 샘플. name은 read_file, description은 파일 내용을 읽는다, input은 path, output은 content 또는 error다. 옆에 실제 호출 한 줄과 결과 한 줄을 붙인다.

확인 질문과 모범 답안: "날짜를 ISO 형식으로 바꾸라"는 문장은 도구인가 절차인가? 절차다. 실제 변환 함수나 명령을 호출하는 수단이 있을 때 그 수단이 도구다.

## S11. OMH 사례: 모델을 바꾸지 않고 틀을 바꾼 이유

원본 v10 S11. OMH 사례: 모델을 바꾸지 않고 틀을 바꾼 이유
시간: 31분부터 36분까지, 5분

S11. OMH 사례: 모델을 바꾸지 않고 틀을 바꾼 이유 (31분부터 36분까지, 5분)

장면과 질문 (예시 초안): 새 CSV 파일을 받았다. 열이 무엇인지, 빈 값이 얼마나 있는지 먼저 알아야 한다. 질문: 모델만 더 좋은 것으로 바꾸면 이 일이 해결될까?

핵심 질문: 왜 모델만 바꾸지 않고 작업 틀을 바꾸는가?

한 문장 정의 (사례): OMH는 기존 OpenCode와 OMO 기반 구성을 오프라인 로컬 환경에 맞게 재구성한 사례다. 설정된 모델 하나와 기존 역할 구성을 유지하면서, 과업에 필요한 도구와 스킬, 작업 절차와 검증을 보강했다. OpenCode는 실행 도구, OMO는 기존 역할과 작업 절차를 제공하는 확장이다.

상세 설명 (세 칸): 실제 제약 → 보강한 도구와 작업 절차 → 확인 가능한 증거와 한계

- 실제 제약: 설치는 로컬 패키지로만 하고, 로컬 파일만 다루며, 모델은 설정된 한 개다.
- 바꾼 것: 데이터 구조를 행 값 없이 보는 기능, 두 파일을 키 기준으로 비교하는 기능(자동 병합 없음), 설치 없이 환경을 진단하는 기능, 민감 정보를 가린 오류 맥락 기능, 글자 수를 결정론적으로 세는 검증 기능을 더했다. 이 기능들의 세부는 발표자 메모에만 둔다.
- 재사용한 것: 기존 역할 구성과 설정된 단일 모델을 재사용했다. 도구 실행에는 기존 허용 정책이 적용되며, 읽기 전용이라는 작업 지시만으로 기술적 접근 차단이 생기지는 않는다. 선택형 엄격 절차(omh-rigorous)는 pstack에서 버그 수정, 기능 구현, 근거 기반 조사 절차를 선별해 적응시킨 것이다. 코드 리뷰 절차는 조사 절차를 검토 작업에 맞춰 구성했다. 검증 계획은 기존 OMO 스킬(verification-planning)과 겹치지 않게 조정했다. 원본 흐름 전체를 무조건 따르지 않는다.
- 확인 가능한 증거와 한계: 설치와 점검 기록, 모의 환경에서의 테스트 결과가 있다. 이 증거는 기능이 연결되었다는 뜻이지 모델 품질을 보장하지 않는다. 실제 사내 모델 품질 비교는 실행하지 않았다.

구체 예시: 장면은 세 단계다. (1) 새 CSV를 받는다. 데이터 구조 점검으로 열, 타입, 빈 값 수, 검사 범위를 보고 행 값은 뺀다. (2) 변경한다. 빈 값 처리 규칙을 적용해 새 파일을 만든다(가상 규칙). (3) 전후를 비교한다. before.csv와 after.csv를 id 기준으로 비교해 추가, 삭제, 변경 행 수를 본다. 입력은 두 파일이고, 출력은 구조 요약과 키 기준 차이 요약이다. 자동 병합은 없다.

헷갈리는 지점:
- 점검 스크립트가 통과했다고 모델이 더 좋아진 것은 아니다. 스크립트 점검은 기능 연결을 확인할 뿐이다.
- 모의(mock) 또는 오프라인 검증은 실제 사내 모델의 품질을 증명하지 않는다.
- 같은 모델의 새 문맥으로 다시 검토해도 독립된 다른 모델의 검토가 되지는 않는다.

화면 구성: 세 칸 가로 배치. 실제 제약 → 바꾼 것 → 확인 가능한 증거와 한계. 가운데 칸에서 재사용한 기반과 우리가 더한 것을 두 색으로 나눈다. 아래 주석: 모델은 재학습하지 않았다.

확인 질문과 모범 답안: 점검 스크립트가 모두 통과했다. 이제 모델이 좋은 답을 낸다고 말해도 될까? 아니다. 통과는 연결과 기능 확인이며, 실제 사내 모델 품질은 따로 측정해야 한다.

전환 질문: 비교 결과가 '차이 없음'으로 나오면 무엇을 더 확인해야 할까?

레이아웃과 도식: 모델과 런타임, 커넥터 상자(인증, 권한, 대상), 외부 서비스. 화살표 라벨: 호출 결과로 확인.

공개 순서와 진행: 장면 20초, 질문 '연결 목록에 보이면 바로 읽을 수 있을까?' 5초에서 10초. 세 칸을 채운 뒤 답한다.

발표자 노트: v10 S13 정의, 세 항목, 헷갈림(도구, MCP). 외부 조회는 하지 않는다고 밝힌다.

## S14. MCP

원본 v10 S14. MCP
시간: 42분부터 45분까지, 3분
출처: docs/plans/slide-content-plan-v10.md S14, docs/production/slide-production-brief-v01.md S14

[v10 원문]
S14. MCP (42분부터 45분까지, 3분)

장면과 질문 (예시 초안): 여러 도구가 파일 목록과 파일 내용을 서로 같은 방식으로 주고받아야 한다. 질문: 도구마다 따로 약속을 만들어야 할까, 공통 약속이 있으면 충분할까?

한 문장 정의: MCP(Model Context Protocol)는 호스트 애플리케이션과 외부 도구 및 자원 서버가 도구 목록 조회, 도구 호출, 자원 읽기를 주고받는 방식을 정한 통신 규약이다.

상세 설명:
- MCP는 프로토콜이다. 메시지 형식과 교환 절차를 정하며, 그 자체가 특정 도구나 제품은 아니다.
- MCP 서버는 도구나 자원을 이 규약에 맞춰 노출하고, 호스트는 그 목록을 모델에 제공할 수 있다.
- 프로토콜이 있다고 인증이 자동으로 되지 않는다. MCP에는 인증 관련 규격도 있지만, 이를 따른다는 사실만으로 접근 권한이 생기지는 않는다. 실제 계정 연결과 허용 범위는 서버와 호스트가 적용한다.

장면에 다시 적용 (예시 초안): 입력: 목록 조회 요청. 출력: 서버가 알려 준 도구 목록과 호출 결과. 공통 약속이 있어도 어떤 폴더를 허용할지는 서버와 호스트 설정이 정한다.

강사용 보충 예시 (화면 생략): CSV를 읽는 MCP 서버가 read_csv 도구를 노출한다. 호스트가 목록을 받아 모델에 보여 주고, 모델이 호출하면 서버가 결과를 돌려준다. 이 설명에서는 MCP 서버 없이 read_file로 같은 일을 한다고 가정한다.

헷갈리는 지점: 도구는 기능이고 MCP는 기능을 주고받는 규칙이다. 모든 도구가 MCP인 것은 아니다. 로컬 함수나 셸 명령은 MCP 없이도 도구가 된다.

화면 구성: 첫 화면은 장면과 질문만 보인다. 답을 공개한 뒤 정의와 적용을 보인다. 호스트 상자(Claude Code 같은 앱)와 MCP 서버 상자 사이에 규약 선을 긋는다. 선 위에 "목록 조회, 도구 호출, 자원 읽기"를 쓰고, 선 아래에 "연결 규약을 따른다는 것과 접근 권한을 얻었다는 것은 다름"이라고 적는다.

확인 질문과 모범 답안: MCP 서버를 연결하면 인증 없이도 모든 데이터를 읽을 수 있는가? 아니다. 인증 관련 규격이 있더라도 실제 계정 연결과 허용 범위를 설정하고 검사해야 한다.

시간: 42분부터 45분까지, 3분. 장면 도입 20초에서 30초와 예측 질문 5초에서 10초를 포함한다.

[제작 브리프]
S14. MCP (42분부터 45분까지, 3분)

레이아웃과 도식: 좌측 호스트, 우측 MCP 서버. 가운데 규약 선에 목록 조회, 도구 호출, 자원 읽기. 아래 주석: 접근 권한은 서버와 호스트 설정이 정함.

필요 자료와 준비 상태: AS-04 범위 컨테이너(변형).

## S15. Grokbot 패턴 비교

[v10 원문]
S15. Grokbot 패턴 비교 (45분부터 48분까지, 3분)

장면과 질문 (예시 초안): 여러 봇이 역할을 나눠 맡고 하나의 공유 공간을 쓴다는 설명을 들었다. 질문: 우리 팀에도 이런 구조가 맞을까?

한 문장 정의: Grokbot은 사용자가 설명한 사례의 패턴이며, 역할별 봇 네 개, 공유 클라우드 환경, 커넥터와 루틴을 비교 틀로만 쓴다. 제품 사양이나 벤치마크가 아니다.

상세 설명:
- 이번 수정에서도 첨부 자료를 열 수 없었다. 이 슬라이드는 이전에 받은 설명 요약만 쓰고, 그 요약도 독립 검증하지 않았다.
- 비교 축은 네 가지다. 누가 책임지는가, 작업이 어디서 실행되는가, 상태가 어디에 남는가, 사람이 어디서 개입하는가.
- 클라우드가 항상 동작한다거나 모든 파일이 전역으로 공유된다거나 구글 브라우저 로그인 제한이 있다고 말하지 않는다.

구체 예시: 책임 축에서 Grokbot 설명은 역할별 봇이 각자 책임을 나눈다고 쓴다. OpenClaw 사례는 코디네이터가 판단하고 워커가 쓰며 부모가 검증한다. CEO Agent 사례는 실무자가 반영 책임을 지고, 에이전트는 초안까지만 낸다.

헷갈리는 지점: 봇이 네 개라고 에이전트가 많이 필요한 것은 아니다. 하네스는 단일 도구와 컨텍스트, 검증만으로도 성립할 수 있다. 공유 클라우드는 실행 위치의 한 형태이고 개입 방식과는 별개다(S32, S33).

화면 구성: 네 축 목록. 각 축마다 Grokbot 설명, OpenClaw 사례, CEO Agent 사례를 한 줄씩 쓴다. 표가 아니라 목록이다. 맨 아래에 "사용자 설명, 첨부 미확인, 패턴 비교만"이라고 적는다.

확인 질문과 모범 답안: 우리 팀 도구를 고른다면 네 축 중 무엇이 가장 중요한가? 정답은 없다. 청중의 답을 받고, 각 축의 책임과 상태 위치를 확인하는 질문으로 마무리한다.

전환 질문: 책임이 여러 봇에 나뉘면 최종 책임은 누가 지고, 사람은 어느 지점에 개입하나?

시간: 45분부터 48분까지, 3분.

[제작 브리프]
S15. Grokbot 패턴 비교 (45분부터 48분까지, 3분)

화면 핵심 문장: 역할별 봇과 공유 환경의 패턴을 비교한다. 제품 벤치마크가 아니다.

레이아웃과 도식: 네 축 목록(책임, 실행 위치, 상태 위치, 사람 개입), 축마다 세 줄(Grokbot 설명, OpenClaw, CEO Agent). 하단: 사용자 설명, 첨부 미확인.

발표자 노트: v10 S15 패턴 비교. 첨부 자료는 열지 못했다. 설명 요약만 쓰고 공유 파일이나 로그인 제한 주장은 하지 않는다. 수치를 새로 만들지 않는다.

필요 자료와 준비 상태: 첨부 미확보. 출처 검증 대기로 표시.

원본 v10 S16. 프롬프트

[v10 원문]
S16. 프롬프트 (48분부터 51분까지, 3분)

장면과 질문 (예시 초안): 회의 준비를 AI에게 맡기면서 두 가지 요청 중 하나를 고른다. 하나는 '회의 준비해 줘'다. 질문: 안건, 참석자, 지난 결정을 넣은 요청과 한 줄 요청 중 어느 쪽이 결과를 더 좌우할까?

한 문장 정의: 프롬프트는 모델에 주는 입력 중 지시, 질문, 역할, 제약을 담은 부분이며, 한 번만 쓰일 수도 있고 여러 실행에 반복되는 지속 지침일 수도 있다.

상세 설명:
- 지속 지침은 파일로 두고, 프롬프트가 그 파일을 읽으라고 지정할 수 있다.
- 프롬프트는 입력의 일부일 뿐이다. 필요한 파일이 빠지면 좋은 문장도 결과를 바꾸지 못한다.
- 완료 기준과 출력 형식을 명시하면 검증이 쉬워진다. 다만 길게 쓴다고 결과가 보장되지는 않는다.

장면에 다시 적용 (예시 초안): 입력 A: '회의 준비해 줘'. 출력 A: 일반 목록. 입력 B: 안건, 참석자, 지난 결정 세 줄을 더한 요청. 출력 B: 안건 중심 준비안. 다만 입력에 없는 사실은 입력을 넣어도 참이라고 보장되지 않으니 확인이 필요하다.

강사용 보충 예시 (화면 생략): 1차 프롬프트는 "이 CSV로 주간 고객 문의 보고서를 써 줘"다. 2차 프롬프트는 "규칙 파일, 작업 절차 파일, 출력 형식 파일, 체크리스트를 먼저 읽고 그 기준대로 작업하라"와 가상의 저장 경로를 담는다. CEO Agent 사례에서도 과업과 독자를 적는 문장이 어떤 등록과 기준을 고를지 정한다(S26).

헷갈리는 지점: 프롬프트는 지시 문장이고, 컨텍스트는 실제로 입력된 전체다(S17). 규칙 파일이 폴더에 있는 것만으로 입력 포함 여부를 확정할 수는 없다. 제품의 자동 지침 탐색이나 명시적 읽기를 통해 실제로 입력됐는지 확인한다.

화면 구성: 첫 화면은 장면과 질문만 보인다. 답을 공개한 뒤 정의와 적용을 보인다. 프롬프트 상자에 실제 문장 두 줄. 아래에 읽을 파일 목록 상자를 두고 규칙, 작업 절차, 출력 형식, 체크리스트 파일로 화살표를 긋는다. 화살표 끝에 "입력에 포함됨"이라고 적는다.

확인 질문과 모범 답안: 규칙 파일을 폴더에 두었지만 프롬프트에 언급하지 않았다. 모델이 그 규칙을 따른다고 확정할 수 있는가? 아니다. 자동 탐색 여부는 도구와 설정에 따라 다르므로, 명시적으로 읽히는지 확인한다.

시간: 48분부터 51분까지, 3분. 장면 도입 20초에서 30초와 예측 질문 5초에서 10초를 포함한다.

[제작 브리프]
S16. 프롬프트 (48분부터 51분까지, 3분)

화면 핵심 문장: 지시와 제약을 담은 입력의 일부이며, 지속 지침일 수도 있다.

레이아웃과 도식: 좌측 요청 두 개를 세로로(한 줄 요청, 파일 읽기 지시). 우측 차이 문구: 같은 모델, 다른 입력.

## S17. 컨텍스트

원본 v10 S17. 컨텍스트
시간: 51분부터 54분까지, 3분
출처: docs/plans/slide-content-plan-v10.md S17, docs/production/slide-production-brief-v01.md S17

[v10 원문]
S17. 컨텍스트 (51분부터 54분까지, 3분)

장면과 질문 (예시 초안): 회의 요청에 안건과 참석자, 지난 결정 사항을 빼고 보낸다. 지난 회의록 파일 경로는 알려 준다. 질문: AI는 지난 회의의 결정을 떠올릴 수 있을까?

한 문장 정의: 컨텍스트는 특정 호출에서 모델이 실제로 입력받은 모든 내용, 즉 지시, 파일 내용, 도구 결과, 이전 대화 중 포함된 부분이다.

상세 설명:

S21. AI교양 좁은 업무 하네스 (63분부터 68분까지, 5분)

장면과 질문 (예시 초안): AI교양 원문이 들어왔다. 최종본은 아직 확정되지 않았는데, 삽화부터 만들어 보자는 요청이 온다. 질문: 확정 전에 삽화를 만들어도 될까?

한 문장 정의: AI교양 제작 흐름은 워크플로우이고, 그 흐름을 반복 가능하게 만드는 규칙, 컨텍스트, 도구, 상태, 검증을 묶으면 좁은 업무용 하네스로 설명할 수 있다. 자동 전환을 강제하는 별도 상태 머신이 구현되었다는 뜻은 아니다.

상세 설명:
- 규칙은 원문 보존과 버전 관리, 확정 문장 불변, 비공개 초안의 범위다. 최종 확정은 사람의 게이트로 남는다.
- 컨텍스트는 해당 글, 수정 이력, 관련 근거를 명시적으로 넣는 것이다.
- 도구는 파일 저장, 이미지 생성, 초안 작성이다. 상태는 현재 버전, 확정 여부, 단계별 결과, 초안 식별자다. 검증은 저장본 대조와 초안 재열람이다.
- 이 사례는 워크플로우 설명과 같은 흐름이지만, 실행을 받치는 장치까지 본다는 점이 다르다.

구체 예시: 완료 기록을 보면 확정 문장을 저장본과 대조해 일치를 확인했고, 삽화를 볼트에 복사한 뒤 해시가 일치함을 확인했다. 비공개 초안은 재열람해 본문, 대표 이미지, 이미지 순서, 카테고리를 확인했고 공개 발행은 하지 않았다. 이 기록은 설명용 인용이며, 이번 작업으로 제작을 실행하지 않았다. 출처는 USER.md의 AI교양 지시와 logs/2026-10-19/ai-literacy-129-production/completion.md다.

헷갈리는 지점: 워크플로우와 하네스는 같은 말이 아니다(S27, S6). 단계만 보면 워크플로우이고, 그 단계를 실행하고 검증하는 장치까지 포함하면 업무용 하네스다. 자동 기록이 있다고 해서 별도의 상태 머신이 자동으로 전환을 강제했다고 말하지 않는다.

화면 구성: 가운데 네 단계 흐름, 주변에 규칙, 컨텍스트, 도구, 상태, 검증 다섯 칸. 각 칸에 AI교양 예시를 한 줄씩 적는다. 주석은 "단계만 보면 워크플로우, 실행을 받치는 장치까지 보면 업무용 하네스"다.

확인 질문과 모범 답안: 이 흐름에서 자동으로 실행되는 것과 사람이 결정하는 것을 나누면? 사용자의 최종 확정은 사람이 결정하고, 저장과 초안 작성과 재열람은 정해진 절차로 실행되며, 공개 발행은 범위 밖이다.

전환 질문: 시작에서 물은 질문으로 돌아가자. 이 단계를 건너뛰지 않게 하는 것은 사람의 확정인가, 기록된 규칙인가?

한 문장 정의: 세션은 하나의 작업 흐름을 묶어 두는 대화와 상태의 단위이며, 입력, 출력, 도구 기록, 진행 상태가 여기에 연결된다.

상세 설명:

- 세션은 실행 주체가 아니다. 실제 파일을 고치는 주체는 워커다(S24).
- 같은 세션을 여러 화면에서 볼 수 있다. 화면이 늘어도 세션과 쓰기 주체는 늘지 않는다.

강사용 보충 예시 (화면 생략): 한 세션에서 초안 보고서를 만들었다. 같은 세션에서 "모호 행 목록을 보강해 줘"라고 하면 이전 결과를 이어받는다. 새 세션을 열면 이 대화를 모르므로 인계 파일을 읽혀야 한다.

헷갈리는 지점: 세션과 워커는 다르다(S24). 세션에 저장된 이력 전체와 현재 컨텍스트는 같지 않다. 저장된 이력 중 이번 호출에 포함된 부분만 컨텍스트이며, 저장 위치만으로 메모리와 컨텍스트를 나누지는 않는다(S20).

상세 설명:
- 서브에이전트는 자기 입력과 지시를 따로 받는다. 상위 대화 전체를 자동으로 공유하지 않는 경우가 많다. 공유 범위는 제품마다 다르다.
- 파일을 고치지 않고 읽고 요약하거나 검색만 하는 읽기 전용 역할도 가능하다.
- 서브에이전트가 있다고 독립 검토가 보장되지는 않는다. 같은 모델과 지침을 쓰면 편향을 공유할 수 있다.

장면에 다시 적용 (예시 초안): 입력: 용어 정의 추출 지시와 문서. 출력: 용어 목록, 원문은 그대로 둔다. 상위 작업이 이 목록을 보고서에 붙인다. 별도 실행이어도 같은 모델과 유사한 맥락에서는 오류가 겹칠 수 있다. 역할을 나눴다는 사실만으로 검증의 독립성을 보장하지 않는다.

강사용 보충 예시 (화면 생략): 모호한 행 목록만 따로 읽고 이유를 정리하는 하위 실행을 맡긴다. 이 서브에이전트는 파일을 쓰지 않는 읽기 전용 역할이다. 결과 목록을 상위 보고서에 붙인다. CEO Agent 사례의 보조 관점 기능은 서브에이전트를 띄우지 않는다(S26).

헷갈리는 지점: 서브에이전트와 워커는 다르다(S24). 서브에이전트와 오케스트레이션도 다르다. 오케스트레이션은 배정 방식이고, 서브에이전트는 실행 단위다(S8).

확인 질문과 모범 답안: 서브에이전트가 "검토 완료"라고 보고했다. 독립 검토가 이루어졌는가? 아니다. 같은 모델과 맥락을 공유하면 독립성이 약하다. 검증 기준을 별도로 확인해야 한다.

[v10 원문]
S26. CEO Agent: 조사한 페르소나를 상황에 맞게 적용하기 (87분부터 90분까지, 3분)

장면과 질문 (예시 초안): 같은 사실을 사내 검토용 보고와 외부 연설용 문장으로 옮겨야 한다. 질문: 같은 사실이라면 강조도 같아야 할까?

이 단계들은 한 작업 흐름의 단계다. 여러 단계가 있다고 서로 독립된 작업자가 되는 것은 아니다.

한 문장 정의: 워크플로는 과업, 독자, 자리에 따라 조사에서 얻은 페르소나, 등록(register), 판단 루브릭을 골라 적용하며, 이 선택이 결과의 말투와 지적 우선순위를 바꾼다.

핵심 메시지: 이 사례에서 중요한 것은 기능 목록이 아니라 페르소나를 어떻게 얻고 어떻게 쓰는가다. 자료를 조사해 특성을 명세로 만들고, 상황에 맞게 골라 쓴다. 모델을 새로 학습한 것이 아니다.

화면 구성 (두 줄 구조):
- 윗줄, 조사 근거(RESEARCH): 본인이 쓴 자료(2024~2026년 레터, 신년사, 기념 메시지, 현장 방문 기록), 본인이 고친 초안의 변경 기록(삭제, 추가, 재작성, 순서 변경), 실제 피드백과 코멘트. 세 항목에서 상황별 특성을 뽑아 페르소나 명세로 만든다. 2차 언론 보도는 보조 근거로만 두고 본인 발언으로 귀속하지 않는다.
- 아랫줄, 실행(EXECUTION): 과업, 독자, 자리를 정한다. 그다음 등록과 판단 기준을 고르고, 관련 맥락만 넣는다. 결과물을 내고 사람의 피드백을 받는다. 피드백은 다시 자료 쪽으로 돌아간다.
- 두 줄 사이에 "관찰된 특성과 가설적 특성은 표시해 구분한다"는 주석을 단다.

상세 설명:
- 페르소나는 말투와 등록을 정하고, 루브릭은 무엇을 지적할지를 정한다. 둘은 서로 다른 명세 파일이다. 둘을 독립된 에이전트 두 개로 말하지 않는다.
- 보조 역할 관점, 예를 들어 재무 관점이나 리스크 관점은 실제 인물을 복사한 것이 아니라 기능적 관점이다.

구체 예시 (가상, 익명): 같은 사실, "분기 일정 지연 두 건, 원인은 외부 승인 대기"를 두 상황에 적용한다. 사내 보고 검수에서는 "지연 두 건의 원인과 조치 기한을 확인할 수 있는가"를 묻는다. 외부 발언에서는 "외부 승인 대기로 분기 일정 두 건이 지연됐다"는 동일한 사실을 청중이 이해할 배경과 함께 설명한다. 구체적인 화법은 해당 상황의 명세에 따른다. 이 예시는 설명용이며 실제 인물의 말투를 단정하지 않는다.

헷갈리는 지점: 이 선택은 모델 학습이 아니다. 입력 맥락과 명세를 고르는 일이다. 페르소나를 골랐다고 사실이 바뀌지는 않는다. 여러 관점이 함께 말한다고 독립 검증이 되지도 않는다.

확인 질문과 모범 답안: 같은 사실을 사내 보고와 외부 연설에 쓰면 결과가 같아야 하는가? 아니다. 독자와 자리에 따라 등록과 강조를 고르는 것이 목적이다. 다만 사실 자체는 같아야 하며, 그 점을 사람이 확인한다.

장면과 질문 (예시 초안): AI교양 최종 확정 메시지가 도착했다. 저장과 비공개 초안 작성을 자동으로 이어 가게 하고 싶다. 질문: 확정 메시지 하나로 뒤의 제작 전체를 자동으로 시작해도 될까?

한 문장 정의: 자동화는 시간, 이벤트, 또는 앞 단계의 결과 같은 조건이 충족되면 정해진 작업을 사람이 다시 시작하지 않아도 실행하도록 만든 장치다.

상세 설명:
- 자동화는 시작 조건과 실행할 작업을 정한다. 실행되었다는 사실이 결과의 옳음을 보장하지는 않는다.
- 실행 기록과 실패 기록을 남겨야 나중에 확인할 수 있다.
- 사람이 결정하는 단계는 자동화 대상에서 빼는 것이 보통이다.

장면에 다시 적용 (예시 초안): 입력: 사용자의 최종 확정 메시지. 자동화가 맡을 수 있는 단계: 확정 문장과 이미지 보존, 비공개 초안 작성, 초안 재열람. 사람이 맡는 단계: 최종 확정 자체. 공개 발행은 자동화 조건에 넣지 않는다. 이 장면은 설명용이며 실행하지 않는다.

강사용 보충 예시 (화면 생략): AI교양 흐름에서 "사용자 최종 확정 메시지"는 이벤트다. 이 이벤트 뒤에 삽화 생성, 보존, 비공개 초안 작성, 재열람 검증을 잇도록 설계할 수 있다. 공개 발행은 조건에 넣지 않는다. 이 설명은 교육용이며, 이번 작업으로 자동화를 설정하거나 실행하지 않았다.

헷갈리는 지점: 자동화와 워크플로우는 다르다(S27). 자동화와 자동 기억도 다르다. 자동 기억은 저장과 불러오기의 문제이고, 자동화는 실행 시작의 문제다(S20).

확인 질문과 모범 답안: 매주 월요일 자동 실행되는 보고서 작업이 있다. 실행 기록에 성공이 찍혔다. 보고서가 맞다고 해도 되는가? 아니다. 성공 기록은 실행이 끝났다는 것만 보여 준다. 검증이 따로 필요하다.

한 문장 정의: 로컬 실행은 도구와 프로세스가 사용자의 컴퓨터에서 돌고, 파일 접근과 명령이 그 기기 안에서 일어나는 방식이며, 모델 추론의 위치와는 별도로 말해야 한다.

상세 설명:
- 로컬은 파일 도구와 명령이 내 기기에서 돈다는 뜻이다. 모델 추론의 위치는 따로 확인한다.
- 로컬 실행이어도 모델을 호출하려면 인터넷과 계정이 필요할 수 있다.
- 로컬 실행이 안전하다는 뜻은 아니다. 권한과 범위 설정이 여전히 필요하다.

장면에 다시 적용 (예시 초안): 입력: 폴더 읽기 요청. 파일 읽기 도구는 노트북에서 실행된다. 요약 요청은 모델 서비스로 나간다. 파일 읽기 위치와 모델 추론 위치를 따로 적는다. 로컬이라는 말은 도구 실행이 내 기기에서 된다는 뜻이다.

헷갈리는 지점: "로컬에서 돌렸다"는 말이 모델도 기기 안에서 돌았다는 뜻은 아니다. 로컬 실행은 실행 위치이고, 리모트 컨트롤은 개입 방식이다(S33).

S32. 클라우드 실행 (105분부터 108분까지, 3분)

장면과 질문 (예시 초안): 모델은 외부 서버에서 초안을 쓰고, 초안 파일은 내 노트북에 저장한다. 질문: 이 작업을 클라우드 작업이라고 한 단어로 불러도 될까?

한 문장 정의: 클라우드 실행은 도구, 워커, 또는 모델 추론 중 일부나 전부가 사용자 기기가 아닌 외부 서버 환경에서 돌아가는 방식이며, 어느 구성 요소가 클라우드인지 함께 말해야 한다.

상세 설명:
- 클라우드는 실행 환경의 위치다. 파일 환경이 서버에 있을 수도 있고, 모델 추론만 서버에 있을 수도 있다.
- 공유 환경, 접근 권한, 상태 저장 위치가 로컬과 다를 수 있다. 공유 범위는 제품 설정에 따르며, 모든 파일이 전역으로 공유된다고 가정하지 않는다.
- 클라우드 서비스가 항상 정상이라고 가정하지 않는다.

장면에 다시 적용 (예시 초안): 입력: 메일 요청. 출력: 초안 텍스트가 노트북에 저장된다. 추론은 클라우드, 파일 저장은 로컬이라고 구성 요소별로 나눠 적는다. 발송은 하지 않는다.

강사용 보충 예시 (화면 생략): 사용자가 제공한 Grokbot 설명에는 공유 클라우드 환경이 나온다(S15). 이번 워크샵은 그 사실을 독립적으로 확인하지 않았다. 이 설명의 예시 폴더는 로컬이다.

헷갈리는 지점: 모델만 클라우드에서 돌고 파일 도구는 로컬일 수 있다. 이를 "클라우드 작업"이라고 한 단어로 묶으면 위치가 흐려진다. 클라우드 실행과 리모트 컨트롤도 다르다(S33).

화면 구성: 첫 화면은 장면과 질문만 보인다. 답을 공개한 뒤 정의와 적용을 보인다. 두 열. 왼쪽 "내 기기" 상자에 도구와 파일, 오른쪽 "외부 서버" 상자에 모델 추론을 넣는다. 구성 요소마다 라벨을 따로 붙이고, 아래에 "클라우드라는 말만으로는 어느 부분인지 알 수 없다"고 적는다.

확인 질문과 모범 답안: 모델 추론은 클라우드에서 하고 파일은 내 노트북에서 고친다. 클라우드 실행인가? 구성 요소별로 답해야 한다. 추론은 클라우드, 파일 도구는 로컬이라고 나눠 말한다.

시간: 105분부터 108분까지, 3분. 장면 도입 20초에서 30초와 예측 질문 5초에서 10초를 포함한다.

장면과 질문 (예시 초안): 노트북에서 돌고 있는 회의 준비 작업을 휴대폰에서 보고 멈추고 싶다. 질문: 휴대폰에서 멈춤을 누르면 작업 장소가 휴대폰으로 옮겨질까?

한 문장 정의: 리모트 컨트롤은 실제 실행을 원래 환경에서 계속하면서, 다른 화면이나 기기에서 그 세션을 보고 지시하거나 중단 신호를 보내는 접근 및 개입 방식이다.

상세 설명:
- 리모트 컨트롤은 실행 위치가 아니라 조작 방식이다. 실행은 원래 기기나 서버에서 돈다.
- 연결되어 있다는 것과 앱에서 같은 세션이 보인다는 것은 다르다. 서버 연결 상태만으로 가시성을 주장하지 않는다.
- 같은 워커를 보고 조종하는 것이지 두 번째 쓰기 주체가 아니다. 앱에서 파일을 따로 고치는 작업자가 생기면 충돌이 난다.
- 참가자에게 필수가 아니다. 권한 우회 옵션도 필수 설정으로 가르치지 않는다. 이 장의 3분 안에서 60초 이내의 시연 또는 정적 화면으로 설명한다. 시연과 녹화 자료는 아직 제작하지 않았다.

장면에 다시 적용 (예시 초안): 입력: 휴대폰에서 중단 신호. 출력: 노트북의 작업이 멈추고 로그가 남는다. 작업 장소는 노트북 그대로이고, 휴대폰은 보기와 중단만 맡는다.

강사용 보충 예시 (화면 생략): 노트북에서 실행 중인 워커 세션에 휴대폰 앱으로 중단 신호를 보낸다. 실행은 노트북에서 멈추고, 파일도 노트북에 그대로 남는다. 강사 시연에서는 로그의 활성 표시와 세션 링크를 확인하는 순서로 보여 준다.

헷갈리는 지점: 리모트 컨트롤은 클라우드 실행과 다르다(S32). 실행 위치와 개입 방식은 별개의 축이다. ACP 같은 다른 연결 경로와도 다르며, 한 경로로 연결되었다고 다른 경로의 앱 가시성이 보장되지는 않는다.

화면 구성: 첫 화면은 장면과 질문만 보인다. 답을 공개한 뒤 정의와 적용을 보인다. 노트북 상자 안에 워커와 파일, 앱 상자 안에 같은 세션 화면과 중단 버튼을 둔다. 두 상자 사이에 양방향 화살표로 "보기와 지시"를 적는다. 파일 상자는 노트북 안에만 두고, "앱은 두 번째 쓰기 주체가 아니다"라고 주석을 단다.

확인 질문과 모범 답안: 휴대폰 앱에서 세션이 보이고, 앱에서 수정을 지시하자 파일이 바뀌었다. 실행 위치는 어디인가? 워커가 원래 돌고 있던 노트북이다. 앱은 보고 지시하는 화면이다.

## S35. 질의응답과 정리

[v10 원문]
S35. 질의응답과 정리 (115분부터 120분까지, 5분)

한 문장 정의: 질의응답은 참가자의 질문을 받아 용어와 다섯 사례를 다시 확인하는 시간이다.

상세 설명:
- 5분 이상으로 확보한다.
- 마무리에서 용어 25개의 위치와 다섯 사례의 공통 요소를 한 번 더 말한다.
- 다음 실행 명령이나 과제는 없다. 참가자에게 실습을 요청하지 않는다.

구체 예시: 질문이 없으면 "가장 헷갈렸던 용어 하나와 그 이유"를 묻고, 해당 슬라이드 번호를 보여 준다.

헷갈리는 지점: 질의응답에서 제품 기능이나 CEO Agent의 실제 성능을 단정하지 않는다. 확인이 필요한 답은 확인 필요라고 말한다.

화면 구성: 질문 받기 화면, 용어 목록 요약, 다섯 사례 요약 한 장.

확인 질문과 모범 답안: "이 방식이면 항상 정확한가요?" 아니다. 기준과 검증으로 점검 가능해질 뿐이며 결과가 보장되지는 않는다.

시간: 115분부터 120분까지, 5분.

S35. 질의응답과 정리 (115분부터 120분까지, 5분)

공개 순서와 진행: 질문이 없으면 '가장 헷갈렸던 용어 하나와 이유'를 묻는다. 참여를 강요하지 않는다.

필요 자료와 준비 상태: 텍스트 색인만.
