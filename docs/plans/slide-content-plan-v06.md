# OpenClaw 하네스 워크샵 슬라이드 내용 기획 v06

이 문서는 실제 슬라이드, PDF, 그림 파일, 실습 파일이 아니라 슬라이드별 내용 정의서다. 발표자가 각 슬라이드에서 무엇을 말하고 무엇을 보여 줄지 정한다. 용어 슬라이드는 한 장에 용어 하나만 다룬다. 이전 버전인 v04와 v01 워크샵 노트는 그대로 두었다.

## 0. 개편 요약

- v04는 용어를 짝지은 개념 슬라이드 아홉 장에 40분을 썼다. v05는 용어 하나당 슬라이드 한 장으로 바꾸었고, 대상 용어는 25개다.
- 용어 설명 시간은 40분에서 60분으로 늘었다. 그만큼 그림과 사례는 줄였다. v04의 루프 시연 7분과 원격 제어 시연 5분은 시간표에서 빠졌다. 루프의 차이는 S6과 S14, 실습 1차와 2차 비교로 옮겼다. 원격 제어는 S27의 3분 안에서 60초 이내 시연 또는 정적 화면으로 다룬다. 시연과 녹화 자료는 아직 제작하지 않았다.
- 참가자 독립 실습은 Claude Code 또는 Codex만으로 진행한다. 준비 3분을 포함해 30분이다. OpenClaw 설치, Remote 설정, 플러그인, MCP, API 키는 요구하지 않는다.
- 전체 시간표는 120분이다. 쉬는 시간 10분, 질의응답 5분을 포함한다. 슬라이드는 S1부터 S37까지 37장이다.

## 1. 학습 목표

1. 모델, 에이전트, 런타임, 하네스, 오케스트레이션, 도구, 스킬, 플러그인, 커넥터, MCP, 프롬프트, 컨텍스트, 토큰, 컨텍스트 창, 메모리, 세션, 워커, 서브에이전트, 워크플로우, 자동화, 완료 보고, 검증, 로컬 실행, 클라우드 실행, 리모트 컨트롤을 각각 설명할 수 있다.
2. 같은 모델이라도 컨텍스트와 도구, 검증 기준이 다르면 결과의 재현성과 점검 가능성이 달라질 수 있음을 설명할 수 있다. 결과가 반드시 좋아진다고 말하지 않는다.
3. 완료 보고와 검증 증거를 구분하고, 결정적으로 확인할 수 있는 검증 항목을 만들 수 있다.
4. 로컬 실행, 클라우드 실행, 리모트 컨트롤을 서로 다른 축으로 설명하고, 구성 요소별로 위치를 말할 수 있다.
5. 규칙, 작업 절차, 출력 형식, 체크리스트, 인계 파일을 명시적으로 읽히는 방식으로 두 번째 세션에 맥락을 넘길 수 있다.

## 2. 공통 예시와 실습 데이터

### 2.1 합성 고객 문의 티켓 CSV

실습 데이터는 합성 고객 문의 티켓 CSV 한 개다. 실제 고객 정보는 없다. 열은 ticket_id, received_at, channel, category, summary, priority, assignee, status, resolved_at이다. 아래는 설명용 발췌이며 실제 데이터 파일은 아직 만들지 않았다.

```
ticket_id,received_at,channel,category,summary,priority,assignee,status,resolved_at
T-1001,2026-10-03 09:12,email,결제,카드 중복 청구 문의,high,담당A,open,
T-1002,10/3/2026,chat,,배송지 변경 요청,긴급!!,,closed,2026-10-04
T-1002,10/3/2026,chat,,배송지 변경 요청,긴급!!,,closed,2026-10-04
```

- 행 식별자는 파일 안의 줄 번호와 ticket_id를 함께 쓴다. 헤더는 1행이므로 위 발췌의 두 번째 데이터 행은 "2행 T-1001"이다.
- 원본 행 수와 고유 티켓 수를 따로 센다. 위 발췌는 데이터 행 3개, 고유 ticket_id 2개다.
- 날짜가 두 가지 이상으로 읽히면 임의로 바꾸지 않는다. 예를 들어 03/04/2026은 3월 4일일 수도 4월 3일일 수도 있으므로 모호 목록에 적는다.
- 분류가 빈 칸, 담당자 없음, 우선순위 표기 혼재, 중복 ticket_id를 의도적으로 넣는다. 전체 행 수는 배포 전에 정한다.

### 2.2 공통 완료 기준

- 보고서 건수는 원본 행 수와 고유 티켓 수를 구분해 적는다.
- 모호한 행은 빠짐없이 목록으로 적는다. 값이 없는 칸은 추정하지 않고 미확인으로 표시한다.
- 주요 주장마다 행 식별자를 인용한다. 중복 ticket_id만으로 행을 합치지 않는다.
- 외부 조회, 메일 발송, 공개 배포는 하지 않는다. 도구 실행은 참가자별 독립 실습 폴더 안에서만 한다.

### 2.3 AI교양 제작 흐름 (S21, S22, S29 공통 사례)

이 흐름은 실제 AI교양 제작 세션의 기록을 교육용으로 정리한 것이다. 이번 작업으로 제작을 실행하지 않는다.

1. 사용자가 원문을 보내면 받은 본문을 v01로 보존하고 정리 노트와 인덱스에 연결한다. 수정본이 오면 새 버전을 만들고 이전 버전은 남긴다.
2. 세션에서 문장과 논지를 다듬고, 필요하면 근거를 확인한다.
3. 사용자가 최종본을 명시적으로 확정한다. 확정 전에는 제작 단계를 열지 않는다.
4. 확정 뒤에는 삽화 한 장을 만들고, 확정 문장과 이미지를 Obsidian에 보존하고, 설정된 광고와 안내 이미지를 넣은 네이버 비공개 초안을 만든다.
5. 초안을 다시 열어 본문, 대표 이미지, 순서, 카테고리를 확인한다. 공개 발행은 이 흐름에 포함되지 않는다.

### 2.4 실습 산출물 위치

- 입력은 실습 폴더의 tickets.csv 한 개다.
- 기준선 보고서는 output/baseline/report.md에 저장한다.
- 보강 보고서는 output/revised/report.md에 저장한다. 기준선은 덮어쓰지 않는다.
- 규칙은 rules.md, 작업 절차는 task.md, 출력 형식은 schema.md, 검증 항목은 checklist.md, 인계 파일은 handoff.md다. 모두 실습 전에 배포할 빈 틀이며, 이번 작업에서는 만들지 않았다.

### S1. 오늘의 학습 목표 (0분부터 2분까지, 2분)

**핵심 메시지:** 공통 용어로 구조를 설명하고, 실제 운영 사례를 읽은 뒤 작은 업무용 작업 틀을 만들어 본다.

**내용과 화면:** 도입 5분, 용어 60분, 사례 10분, 휴식 10분, 실습 30분, 질문 5분을 시간 막대로 보여 준다. 특정 제품 설치보다 용어와 적용 원리를 다룬다.

**진행:** 모델, 실행, 맥락, 검증을 구분하는 것이 오늘의 목표라고 설명한다.

**시간:** 0분부터 2분까지, 2분.

### S2. 공통 예시와 실습 전제 (2분부터 5분까지, 3분)

**핵심 메시지:** 개념은 문의 CSV와 AI교양 제작의 실제 장면으로 설명하고, 참가자는 Claude Code 또는 Codex 하나로 실습한다.

**내용과 화면:** CSV 세 행과 보고서 목차를 왼쪽에, Claude Code와 Codex의 두 실습 경로를 오른쪽에 둔다. 워크플로우는 AI교양 사례로 설명한다. 참가자는 설치와 로그인을 마친 폴더 읽기/쓰기 가능 환경을 준비하며 OpenClaw, Remote, MCP 설치는 요구하지 않는다.

**진행:** 설치가 안 된 참가자는 준비된 환경이 있는 참가자와 짝을 이룬다. 실습 파일 배포와 시연 자료 제작은 아직 실행하지 않은 후속 준비 사항임을 밝힌다.

**시간:** 2분부터 5분까지, 3분.

## 3. 용어 슬라이드 S3부터 S27

각 슬라이드 제목은 용어 하나다. 헷갈리는 지점에서 이웃 용어와 비교하지만 주제는 그 용어 하나로 유지한다. 단계 제목은 설명 순서를 보여 줄 뿐이며, 한 슬라이드에 여러 용어를 묶지 않는다.

### 단계 A: 실행 주체와 틀

### S3. 모델 (5분부터 7분까지, 2분)

**한 문장 정의:** 모델은 입력된 텍스트와 맥락을 받아 다음 출력을 생성하는 학습된 계산 장치이며, 그 출력에는 답변 텍스트와 도구 호출 요청이 포함될 수 있다.

**상세 설명:**
- 모델은 실행 중에 파일을 열거나 명령을 실행하지 않는다. 입력을 받아 출력을 계산해 내보낸다.
- 도구가 필요하면 "이 도구를 이 인자로 호출해 달라"는 구조화된 요청을 출력한다. 실제 호출은 런타임이 한다(S5).
- 같은 모델이라도 입력과 설정이 다르면 출력이 달라진다. 모델 이름이 결과 전체를 정하지는 않는다.

**구체 예시:** "tickets.csv에 몇 행이 있는가"라는 질문에서 CSV 내용이 입력에 들어 있어야 모델이 그 내용을 근거로 답할 수 있다. 경로만 주고 내용을 넣지 않으면 모델은 파일을 보지 못하고 그럴듯한 숫자를 추측할 수 있다.

**헷갈리는 지점:** 모델과 에이전트는 다르다. 모델은 출력을 만들고, 에이전트는 그 출력이 도구 실행과 결과 확인으로 이어져 여러 단계를 도는 구성이다(S4).

**화면 구성:** 입력 상자(프롬프트 한 줄과 CSV 발췌 세 줄), 모델 상자, 출력 상자 두 개를 가로로 배치한다. 출력 상자 하나는 텍스트 답변, 다른 하나는 read_file(path=tickets.csv) 요청이다. 모델 상자 옆에 "여기서는 파일이 열리지 않는다"는 주석을 단다.

**확인 질문과 모범 답안:** 모델이 "tickets.csv를 읽겠다"고 요청했다. 파일은 이미 읽힌 것인가? 아니다. 요청만 나온 것이며, 런타임이 도구를 실행해 결과를 돌려준 뒤에야 파일 내용이 입력에 들어간다.

**시간:** 5분부터 7분까지, 2분.

### S4. 에이전트 (7분부터 9분까지, 2분)

**한 문장 정의:** 에이전트는 목표를 받아 모델의 판단, 도구 실행, 결과 확인을 반복하며, 종료 조건이 충족될 때까지 작업을 이어 가는 실행 구성이다.

**상세 설명:**
- 핵심은 반복 루프다. 모델이 다음 행동을 고르고, 도구 결과를 보고, 다시 다음 행동을 고른다. 필요하면 다음 행동을 선택해 실행을 이어갈 수 있는 구조가 핵심이다. 실제 응답 횟수만으로 에이전트 여부를 판정하지 않는다.
- 루프를 끝내는 조건이 있어야 한다. 예를 들어 "보고서가 저장되고 체크리스트 항목이 모두 통과하면 종료"다.
- 한 실행 주체가 여러 단계를 도는 것도 에이전트 구성이다. 여러 에이전트가 있어야 하는 것은 아니다.

**구체 예시:** 목표는 "tickets.csv로 보고서를 쓰고 output/baseline/report.md에 저장하라. 체크리스트를 통과하면 끝낸다"이다. 행동은 CSV 열기, 행 수 세기, 빈 칸 목록 만들기, 보고서 쓰기, 체크리스트 대조 순서다. 실패 항목이 있으면 보고서 쓰기로 돌아간다.

**헷갈리는 지점:** 에이전트와 모델은 다르다(S3). 에이전트와 서브에이전트도 다르다. 서브에이전트는 에이전트 안에서 나온 하위 실행이며, 모든 에이전트가 가지는 것은 아니다(S20).

**화면 구성:** 원형 루프. 노드는 목표와 종료 기준, 모델 판단, 도구 실행, 결과 확인, 종료 조건 판단이다. 종료 조건에서 "아니오"는 모델 판단으로, "예"는 종료로 간다. 루프 밖에 목표 문장과 종료 기준 문장을 적는다.

**확인 질문과 모범 답안:** 모델이 보고서를 한 번 쓰고 끝났다. 에이전트인가? 한 번에 끝났다는 사실만으로는 판단할 수 없다. 도구 결과를 보고 후속 행동이나 종료를 정할 수 있는 실행 구조인지 확인해야 한다.

**시간:** 7분부터 9분까지, 2분.

### S5. 런타임 (9분부터 12분까지, 3분)

**한 문장 정의:** 런타임은 모델의 도구 호출 요청을 받아 권한을 확인한 뒤 도구를 실행하고, 결과를 다시 모델 입력으로 돌려주며 다음 호출을 이어 주는 실행 계층이다.

**상세 설명:**
- 모델은 요청만 만든다. 런타임이 요청이 등록된 도구인지, 실행 권한이 있는지 확인한 뒤 실행을 연결한다.
- 실행 결과, 즉 파일 내용, 오류 메시지, 종료 코드를 정리해 다음 모델 호출의 입력에 넣는다. 이 되돌림이 루프를 가능하게 한다.
- 도구가 내 기기에서 도는지 외부 서버에서 도는지는 런타임 구성에 따라 달라진다(S25, S26).
- 여기서 말하는 런타임은 Python이나 Node.js 같은 언어 실행 환경과 다르다. 런타임 전체를 하네스라고 부르지도 않는다(S6).

**구체 예시:** 모델이 read_file(path=tickets.csv)를 요청한다. 런타임이 등록된 파일 읽기 도구를 실제 권한 설정에 따라 실행해 결과를 모델 입력에 넣는다. 실습 폴더만 다루라는 문서 지시가 기술적 접근 차단을 자동으로 만드는 것은 아니다. 파일이 없었다면 "파일 없음" 오류가 돌아가고, 모델은 그 오류를 보고 다음 행동을 고른다.

**헷갈리는 지점:** 모델은 판단과 생성을 맡고, 런타임은 실행을 연결한다. 하네스는 컨텍스트, 도구, 상태, 검증까지 포함하는 더 넓은 틀이다(S6). 명명 경계는 제품마다 다를 수 있다.

**화면 구성:** 순서도. 모델 요청 → 런타임(권한 확인, 도구 실행) → 파일 읽기 도구 → 결과 → 런타임(결과 정리) → 모델 입력 → 모델 다음 판단. 모델과 런타임 상자는 테두리 색을 다르게 하고, "파일은 런타임 쪽에서만 열린다"는 주석을 단다.

**확인 질문과 모범 답안:** 모델이 파일 읽기를 요청했는데 접근이 차단됐다. 답변 내용만 보면 되는가? 아니다. 권한 기록과 도구 오류 결과를 함께 봐야 한다. 답변이 그럴듯해도 실행 결과가 없을 수 있다.

**시간:** 9분부터 12분까지, 3분.

### S6. 하네스 (12분부터 15분까지, 3분)

**한 문장 정의:** 하네스는 모델이 안정적으로 일하도록 컨텍스트, 도구와 실행 위치, 상태 저장, 검증 절차를 묶은 작업 틀 전체다. 이 워크샵은 이 정의를 쓰며, 제품마다 범위가 다를 수 있다.

**상세 설명:**
- 컨텍스트 구성: 어떤 지침과 입력 파일을 모델에 넣을지 정한다. 예를 들어 rules.md와 tickets.csv를 명시적으로 읽힌다.
- 도구와 실행 위치, 상태와 검증: 어떤 도구를 쓸지, 결과 버전과 인계 파일을 어디에 남길지, 완료를 무엇으로 판단할지 정한다.
- 하네스를 바꾸는 것과 모델을 교체하거나 재학습하는 것은 별개다. 같은 모델이라도 틀이 다르면 재현성과 점검 가능성이 달라진다. 결과가 반드시 좋아진다는 보장은 없다.

**구체 예시:** Claude Code나 Codex는 한 줄 요청을 받는 경우에도 기본 하네스가 있다. 이 예시는 하네스가 없고 있는 비교가 아니라, 기본 실행에 업무용 구성을 얼마나 더했는지의 비교다. 보강된 실행은 같은 CSV에 rules.md, schema.md, checklist.md를 명시적으로 읽히고, 결과를 output/revised/에 저장하며, handoff.md를 남긴다.

**헷갈리는 지점:** 하네스와 오케스트레이션은 다르다. 하네스는 틀이고, 오케스트레이션은 그 안에서 순서와 역할을 배정하는 일이다(S7). 하네스와 런타임도 다르다. 런타임은 실행을 연결하는 층이다.

**화면 구성:** 가운데 원 안에 다섯 칸, 컨텍스트, 도구, 실행 위치, 상태, 검증을 두고 각 칸에 실제 파일명을 적는다. 예를 들어 컨텍스트 칸은 rules.md, 상태 칸은 handoff.md, 검증 칸은 checklist.md다. 원 바깥에 모델 상자 하나가 연결된다.

**확인 질문과 모범 답안:** 검증 체크리스트 파일은 하네스의 어느 칸에 속하는가? 검증 칸이다. 완료 판단 기준을 담기 때문이다. 상태 칸은 진행 기록을 담는다.

**시간:** 12분부터 15분까지, 3분.

### S7. 오케스트레이션 (15분부터 18분까지, 3분)

**한 문장 정의:** 오케스트레이션은 여러 단계나 여러 실행 주체에 일의 순서, 입출력, 역할, 다음 단계로 넘어가는 조건을 배정하고 조율하는 일이다.

**상세 설명:**
- 순서: 무엇을 먼저 하고 나중에 할지 정한다. 예를 들어 원본 행 확인이 끝난 뒤에만 집계한다.
- 역할: 누가 기획, 실행, 검토를 맡는지 정한다. 한 사람이 역할을 번갈아 맡아도 역할 정의는 필요하다.
- 여러 실행 주체가 필요하다는 뜻은 아니다. 단일 에이전트 안의 단계 배정도 오케스트레이션이다.

**구체 예시:** AI교양 제작에서 원문 보존은 먼저 하고, 사용자가 최종본을 확정한 뒤에만 삽화 단계를 연다(2.3). 이 순서와 전환 조건을 정하는 것이 오케스트레이션이다.

**헷갈리는 지점:** 계획된 역할만으로 독립 검토자가 존재한다고 증명되지 않는다. 워크플로우는 단계 흐름 자체이고, 오케스트레이션은 그 흐름을 누가 맡는지 배정하는 조율이다(S21).

**화면 구성:** 세로 레인 세 개, 기획, 실행, 검토를 두고 가로축을 시간으로 한다. 각 레인 칸에 산출물 이름을 적는다. 기획 칸은 체크리스트 초안, 실행 칸은 output/revised/report.md, 검토 칸은 체크 결과다. 전환 화살표에는 전환 조건을 적는다.

**확인 질문과 모범 답안:** 사람이 같은 날 기획, 실행, 검토를 차례로 맡았다. 독립 검토인가? 아니다. 역할이 나뉘어 있을 뿐이며, 같은 사람과 같은 맥락의 편향이 남는다. 역할 연습으로만 본다.

**시간:** 15분부터 18분까지, 3분.

### 단계 B: 능력과 입력

### S8. 도구 (18분부터 20분까지, 2분)

**한 문장 정의:** 도구는 모델이 요청하고 런타임이 실행하는, 이름과 입력 형식과 결과 형식이 정해진 호출 가능한 기능이다.

**상세 설명:**
- 도구에는 이름, 설명, 입력 형식, 결과 형식이 있다. 모델은 이 설명을 보고 어떤 도구를 쓸지 고른다.
- 파일 읽기, 파일 쓰기, 명령 실행, 검색처럼 실제 효과를 내는 기능이다.
- 도구가 있다고 항상 쓰이지는 않는다. 모델이 판단하고, 런타임이 권한을 확인한다.

**구체 예시:** read_file(path=tickets.csv)는 파일 내용을 돌려준다. write_file(path=output/revised/report.md, content=...)는 보고서를 저장한다. 두 호출 모두 입력과 결과 형식이 정해져 있다.

**헷갈리는 지점:** 도구는 절차가 아니다. "날짜를 ISO 형식으로 바꾼다"는 절차이고, 그 변환을 실행하는 함수 호출이 도구다. 도구와 MCP도 다르다. MCP는 도구를 연결하는 통신 규약이다(S12).

**화면 구성:** 도구 카드 샘플. name은 read_file, description은 파일 내용을 읽는다, input은 path, output은 content 또는 error다. 옆에 실제 호출 한 줄과 결과 한 줄을 붙인다.

**확인 질문과 모범 답안:** "날짜를 ISO 형식으로 바꾸라"는 문장은 도구인가 절차인가? 절차다. 실제 변환 함수나 명령을 호출하는 수단이 있을 때 그 수단이 도구다.

**시간:** 18분부터 20분까지, 2분.

### S9. 스킬 (20분부터 22분까지, 2분)

**한 문장 정의:** 스킬은 특정 종류의 작업에 대한 절차, 입력과 출력 규칙, 필요한 자원을 묶어 다시 쓸 수 있게 만든 지침 묶음이다.

**상세 설명:**
- 스킬은 주로 절차를 설명한 파일이 중심이며, 참고 자료나 스크립트를 함께 담을 수 있다.
- 스킬 자체는 실행되지 않는다. 스크립트가 있어도 실행은 런타임과 도구가 맡는다.
- 포장과 호출 방식은 도구마다 다르다. 여러 도구에서 그대로 옮겨 쓸 수 있다고 주장하지 않는다.

**구체 예시:** "고객 문의 보고서 작성" 스킬 후보는 입력이 tickets.csv, 출력이 보고서 파일이다. 절차는 행 수 세기, 중복 확인, 모호 행 목록, 보고서 쓰기, 체크리스트 대조다. 절차 설명 파일 하나와 체크리스트 파일 하나로 구성할 수 있다.

**헷갈리는 지점:** 스킬은 도구가 아니다(S8). 플러그인과도 다르다. 플러그인은 여러 기능과 지침을 배포하는 포장이며(S10), 스킬이 있다고 결과가 자동으로 맞아지지는 않는다.

**화면 구성:** 예시 폴더 구조. report-skill 폴더 아래 절차 설명 파일, checklist.md, schema.md, 선택 사항인 scripts 폴더가 있다. scripts 옆에 "실행은 런타임과 도구가 맡음"이라고 적는다.

**확인 질문과 모범 답안:** 스킬 폴더에 파이썬 스크립트가 있다. 스킬이 스스로 실행되는가? 아니다. 누군가 호출해야 하고, 실행은 런타임과 도구가 한다.

**시간:** 20분부터 22분까지, 2분.

### S10. 플러그인 (22분부터 24분까지, 2분)

**한 문장 정의:** 플러그인은 여러 기능과 지침과 설정을 한 번에 설치하고 버전으로 관리하기 위해 배포하는 패키지 단위이며, 포함 범위와 설치 방식은 호스트 제품마다 다르다.

**상세 설명:**
- 플러그인은 포장이다. 안에 스킬, 도구 설정, 커넥터 설정이 일부 또는 전부 들어 있을 수 있다.
- 포장 구조와 이름 규칙은 제품마다 다르다. 같은 플러그인이 모든 도구에서 같은 방식으로 작동한다고 가정하지 않는다.
- 설치가 끝났다고 외부 계정 인증과 권한 허용이 자동으로 끝나지는 않는다.

**구체 예시:** 주간 보고서 플러그인이 보고서 스킬, 체크리스트, 외부 메일 커넥터 설정을 묶었다고 하자. 실습에서는 메일 커넥터를 쓰지 않으므로 빼고, 스킬이라는 개념만 본다.

**헷갈리는 지점:** 플러그인은 MCP가 아니다. MCP 서버 설정이 플러그인 안에 들어갈 수는 있지만 두 층은 다르다(S12). 플러그인은 배포 단위이고, 스킬은 절차 단위다.

**화면 구성:** 플러그인 상자 하나 안에 스킬, 도구 설정, 커넥터 설정 세 칸. 바깥에 "설치는 포장을 가져오는 단계, 인증은 별도 단계"라는 주석을 단다.

**확인 질문과 모범 답안:** 플러그인을 설치했으니 외부 계정 접근도 자동으로 된다고 해도 되는가? 아니다. 설치, 계정 인증, 권한 허용을 각각 확인해야 한다.

**시간:** 22분부터 24분까지, 2분.

### S11. 커넥터 (24분부터 26분까지, 2분)

**한 문장 정의:** 커넥터는 모델과 런타임이 외부 서비스, 데이터 저장소, 다른 앱의 기능에 접근하도록 만든 연결 지점이며, 연결 설정과 인증 절차를 포함한다.

**상세 설명:**
- 커넥터는 대상 서비스와의 연결 설정과 인증을 가진다. 제품에 따라 앱 연동, 통합이라고 부르기도 한다.
- 외부 데이터를 읽거나 쓸 때 실제 권한 범위는 연결에 사용한 계정, 대상 서비스 정책, 커넥터와 런타임 설정이 함께 정한다.
- 목록에 보이는 것과 실제로 호출이 되는 것은 다르다. 호출해 봐야 안다.

**구체 예시:** 고객 문의 시스템 API에 연결된 커넥터가 있으면 최신 티켓을 가져올 수 있다. 실습에서는 외부 조회를 하지 않으므로 같은 흐름을 로컬 tickets.csv로 대체한다.

**헷갈리는 지점:** 커넥터는 외부와의 연결 지점이고, 도구는 모델이 호출하는 기능이다. 커넥터 하나가 여러 도구를 노출할 수 있다. 커넥터가 MCP 방식으로 노출될 수도 있지만, MCP는 연결을 주고받는 규약이다(S12).

**화면 구성:** 모델과 런타임 상자에서 화살표가 커넥터 상자로 간다. 커넥터 상자 안에 인증, 권한 범위, 대상 서비스 세 칸을 두고, 끝에 외부 서비스 상자를 둔다. 옆에 "호출 성공 여부는 실제 호출 결과로 확인"이라고 적는다.

**확인 질문과 모범 답안:** 커넥터 목록에 항목이 보이면 바로 데이터를 읽을 수 있는가? 아니다. 인증과 권한이 살아 있는지, 실제 호출이 성공하는지 확인해야 한다.

**시간:** 24분부터 26분까지, 2분.

### S12. MCP (26분부터 28분까지, 2분)

**한 문장 정의:** MCP(Model Context Protocol)는 호스트 애플리케이션과 외부 도구 및 자원 서버가 도구 목록 조회, 도구 호출, 자원 읽기를 주고받는 방식을 정한 통신 규약이다.

**상세 설명:**
- MCP는 프로토콜이다. 메시지 형식과 교환 절차를 정하며, 그 자체가 특정 도구나 제품은 아니다.
- MCP 서버는 도구나 자원을 이 규약에 맞춰 노출하고, 호스트는 그 목록을 모델에 제공할 수 있다.
- 프로토콜이 있다고 인증이 자동으로 되지 않는다. MCP에는 인증 관련 규격도 있지만, 이를 따른다는 사실만으로 접근 권한이 생기지는 않는다. 실제 계정 연결과 허용 범위는 서버와 호스트가 적용한다.

**구체 예시:** CSV를 읽는 MCP 서버가 read_csv 도구를 노출한다. 호스트가 목록을 받아 모델에 보여 주고, 모델이 호출하면 서버가 결과를 돌려준다. 실습에서는 MCP 서버를 띄우지 않고 read_file로 같은 일을 한다.

**헷갈리는 지점:** 도구는 기능이고 MCP는 기능을 주고받는 규칙이다. 모든 도구가 MCP인 것은 아니다. 로컬 함수나 셸 명령은 MCP 없이도 도구가 된다.

**화면 구성:** 호스트 상자(Claude Code 같은 앱)와 MCP 서버 상자 사이에 규약 선을 긋는다. 선 위에 "목록 조회, 도구 호출, 자원 읽기"를 쓰고, 선 아래에 "연결 규약을 따른다는 것과 접근 권한을 얻었다는 것은 다름"이라고 적는다.

**확인 질문과 모범 답안:** MCP 서버를 연결하면 인증 없이도 모든 데이터를 읽을 수 있는가? 아니다. 인증 관련 규격이 있더라도 실제 계정 연결과 허용 범위를 설정하고 검사해야 한다.

**시간:** 26분부터 28분까지, 2분.

### 단계 C: 입력의 구성과 한계

### S13. 프롬프트 (28분부터 30분까지, 2분)

**한 문장 정의:** 프롬프트는 모델에 주는 입력 중 지시, 질문, 역할, 제약을 담은 부분이며, 한 번만 쓰일 수도 있고 여러 실행에 반복되는 지속 지침일 수도 있다.

**상세 설명:**
- 지속 지침은 파일로 두고, 프롬프트가 그 파일을 읽으라고 지정할 수 있다.
- 프롬프트는 입력의 일부일 뿐이다. 필요한 파일이 빠지면 좋은 문장도 결과를 바꾸지 못한다.
- 완료 기준과 출력 형식을 명시하면 검증이 쉬워진다. 다만 길게 쓴다고 결과가 보장되지는 않는다.

**구체 예시:** 1차 프롬프트는 "이 CSV로 주간 고객 문의 보고서를 써 줘"다. 2차 프롬프트는 "rules.md, task.md, schema.md, checklist.md를 먼저 읽고 그 기준대로 작업하라"와 output/revised/report.md 저장 지시를 담는다.

**헷갈리는 지점:** 프롬프트는 지시 문장이고, 컨텍스트는 실제로 입력된 전체다(S14). 규칙 파일이 폴더에 있는 것만으로 입력 포함 여부를 확정할 수는 없다. 제품의 자동 지침 탐색이나 명시적 읽기를 통해 실제로 입력됐는지 확인한다.

**화면 구성:** 프롬프트 상자에 실제 문장 두 줄. 아래에 읽을 파일 목록 상자를 두고 rules.md, task.md, schema.md, checklist.md로 화살표를 긋는다. 화살표 끝에 "입력에 포함됨"이라고 적는다.

**확인 질문과 모범 답안:** 규칙 파일을 폴더에 두었지만 프롬프트에 언급하지 않았다. 모델이 그 규칙을 따른다고 확정할 수 있는가? 아니다. 자동 탐색 여부는 도구와 설정에 따라 다르므로, 실습에서는 프롬프트에 명시한다.

**시간:** 28분부터 30분까지, 2분.

### S14. 컨텍스트 (30분부터 33분까지, 3분)

**한 문장 정의:** 컨텍스트는 특정 호출에서 모델이 실제로 입력받은 모든 내용, 즉 지시, 파일 내용, 도구 결과, 이전 대화 중 포함된 부분이다.

**상세 설명:**
- 컨텍스트는 실제로 입력에 들어간 것만 포함한다. 디스크에 파일이 있다고 해서 컨텍스트에 있는 것은 아니다.
- 파일을 읽었다는 도구 기록이 있어도 앞부분만 들어갔다면 모델은 전체를 본 것이 아니다.
- 이전 대화와 도구 결과가 쌓이면 커지고, 크기에는 한계가 있다(S16).

**구체 예시:** tickets.csv가 40행인데 도구가 앞 20행만 읽어 입력에 넣었다. 모델의 답은 20행 기준이다. 보고서에 "전체 40행 중"이라고 쓰면 근거가 빠진 주장이다. 체크리스트의 원본 행 수 항목이 이것을 잡는다.

**헷갈리는 지점:** 컨텍스트와 메모리는 다르다. 메모리는 나중에 불러오도록 저장된 정보이고, 컨텍스트는 지금 입력에 들어 있는 정보다(S17).

**화면 구성:** 입력 덩어리를 칸으로 나눈다. 지시, rules.md 내용, tickets.csv 앞 20행, 도구 결과, 이전 대화. 칸 밖에 디스크에 있지만 입력되지 않은 파일 목록을 두고, 안과 밖을 색으로 구분한다.

**확인 질문과 모범 답안:** 디스크에 checklist.md가 있다. 모델은 이 체크리스트를 알고 있는가? 파일을 읽어 입력에 넣기 전에는 모른다. 디스크에 있는 것과 컨텍스트에 포함된 것은 다르다.

**시간:** 30분부터 33분까지, 3분.

### S15. 토큰 (33분부터 35분까지, 2분)

**한 문장 정의:** 토큰은 모델이 입력과 출력을 처리할 때 세는 텍스트 조각의 단위이며, 단어 수나 글자 수와 같지 않다.

**상세 설명:**
- 토큰은 모델의 내부 분할 방식에 따라 나뉘므로 단어 수와 일치하지 않는다.
- 언어와 문자에 따라 같은 글자 수라도 토큰 수가 다를 수 있다. 한국어 글자당, 영어 단어당 토큰 수 같은 보편적 비율은 없다.
- 정확한 수는 해당 모델이 제공하는 계산 방식으로 확인한다. 이번 워크샵에서는 추정하지 않는다.

**구체 예시:** 같은 보고서 내용을 한국어로 쓰든 영어로 쓰든, 글자 수나 단어 수만 보고 토큰 수를 짐작하면 틀릴 수 있다. 분할 방식이 다르기 때문이다.

**헷갈리는 지점:** 토큰은 측정 단위다. 컨텍스트 창은 그 단위로 잰 한계다(S16).

**화면 구성:** 한 문장을 가상의 조각으로 나눈 예시 한 줄. 칸 아래에 "실제 분할은 모델마다 다르다"는 주석을 단다. 정확한 개수를 보여 주는 계산기 화면은 쓰지 않는다.

**확인 질문과 모범 답안:** 보고서가 500단어라면 토큰도 500개인가? 아니다. 토큰 수는 단어 수와 다르며, 언어와 모델의 분할 방식에 따라 달라진다.

**시간:** 33분부터 35분까지, 2분.

### S16. 컨텍스트 창 (35분부터 38분까지, 3분)

**한 문장 정의:** 컨텍스트 창은 모델이 한 번의 호출에서 입력과 출력을 함께 처리할 수 있는 토큰 범위의 한계다.

**상세 설명:**
- 창은 입력 전체와 출력 생성 분량을 함께 담는다. 입력이 많이 차면 출력에 쓸 공간이 줄어든다.
- 창 크기는 모델과 제품 설정마다 다르다. 수치는 해당 제품 문서로 확인한다.
- 창이 차면 이전 내용을 요약하거나 제거하는 압축이 일어날 수 있다. 압축은 세부를 모두 보존하지 않는다.

**구체 예시:** 긴 CSV 전체, 규칙, 이전 대화를 한 번에 넣으면 한계에 닿을 수 있다. 규칙 파일, 체크리스트, CSV 앞부분, 집계 파일만 읽히면 나눠서 할 수 있다. 워크샵 CSV가 창에 들어가는지는 실습 도구에서 확인해야 한다.

**헷갈리는 지점:** 컨텍스트 창은 한 호출의 크기 한계다. 컨텍스트는 그 안에 실제로 들어간 내용이다(S14). 압축은 현재 창을 줄이는 일이고, 메모리는 호출 밖에 저장해 나중에 다시 불러오는 일이다(S17).

**화면 구성:** 가로 막대 하나. 앞부분에 지시, 파일, 이전 대화를 칸으로 나누고, 뒷부분에 출력 공간을 둔다. 막대 끝에 한계선을 긋고, 옆에 압축 화살표와 "이전 대화 요약, 세부 일부 손실 가능"을 적는다.

**확인 질문과 모범 답안:** 입력이 창을 거의 채우면 앞부분이 무조건 지워지는가? 아니다. 압축이나 잘림이 실제 발생했는지 확인해야 한다. 입력에 규칙이 남아 있어도 준수는 별도로 검증하며, 필요한 시점에 핵심 규칙을 다시 읽힐 수 있다.

**시간:** 35분부터 38분까지, 3분.

### S17. 메모리 (38분부터 41분까지, 3분)

**한 문장 정의:** 메모리는 세션이나 실행이 끝난 뒤에도 나중에 다시 불러올 수 있도록 파일이나 저장소에 남긴 정보이며, 모델의 가중치를 바꾸지 않는다.

**상세 설명:**
- 메모리는 저장된 정보다. 다음 실행에서 필요한 파일을 찾아 읽어 컨텍스트에 넣어야 쓰인다.
- 메모리 검색이 모든 노트를 항상 불러온다는 뜻은 아니다. 무엇을 불러올지는 제품 규칙과 검색 방식에 따라 다르다.
- 재학습이 아니다. 가중치는 그대로이고 입력에 무엇이 들어가는지만 달라진다.

**구체 예시:** 2차 실행 후 handoff.md에 "모호 행 7건, 날짜 규칙 적용 결과 3건 미확인"을 적는다. 3차 세션이 이 파일을 읽으면 미확인 항목부터 이어갈 수 있다. 읽히지 않으면 이 내용을 모른다.

**헷갈리는 지점:** 메모리와 컨텍스트는 다르다(S14). 메모리와 세션도 다르다. 세션이 이어진다고 메모리가 생기는 것은 아니다(S18).

**화면 구성:** 저장소 상자(handoff.md, 노트 파일)에서 읽기 화살표가 컨텍스트 상자로 간다. 저장소 옆에 "자동으로 전부 로드되지 않음"과 "가중치는 변하지 않음"이라고 적는다.

**확인 질문과 모범 답안:** 어제 세션에서 말한 내용을 오늘 모델이 아는가? 세션 복원, 메모리 검색, 파일 읽기 등으로 그 내용이 현재 입력에 실제 포함됐는지 확인해야 한다. 재학습으로 기억이 생긴 것은 아니다.

**시간:** 38분부터 41분까지, 3분.

### 단계 D: 실행 단위와 주체

### S18. 세션 (41분부터 43분까지, 2분)

**한 문장 정의:** 세션은 하나의 작업 흐름을 묶어 두는 대화와 상태의 단위이며, 입력, 출력, 도구 기록, 진행 상태가 여기에 연결된다.

**상세 설명:**
- 같은 세션을 다시 열면 이전 대화가 이어질 수 있다. 이어짐의 범위는 제품 기능에 따라 다르다.
- 세션은 실행 주체가 아니다. 실제 파일을 고치는 주체는 워커다(S19).
- 같은 세션을 여러 화면에서 볼 수 있다. 화면이 늘어도 세션과 쓰기 주체는 늘지 않는다.

**구체 예시:** 1차 세션에서 output/baseline/report.md를 만들었다. 같은 세션에서 "모호 행 목록을 보강해 줘"라고 하면 이전 결과를 이어받는다. 새 세션을 열면 이 대화를 모르므로 handoff.md를 읽혀야 한다.

**헷갈리는 지점:** 세션과 워커는 다르다(S19). 세션에 저장된 이력 전체와 현재 컨텍스트는 같지 않다. 저장된 이력 중 이번 호출에 포함된 부분만 컨텍스트이며, 저장 위치만으로 메모리와 컨텍스트를 나누지는 않는다(S17).

**화면 구성:** 세션 상자 안에 대화 이력, 도구 기록, 상태 파일 링크 세 칸. 바깥에 화면 A와 화면 B를 그리고 둘 다 같은 세션 상자를 가리키게 한다. "화면 두 개, 세션 하나"라고 적는다.

**확인 질문과 모범 답안:** 같은 세션 링크를 두 기기에서 열었다. 워커가 두 개인가? 아니다. 같은 세션을 보는 화면이 둘일 뿐이며, 쓰기 주체는 하나여야 한다.

**시간:** 41분부터 43분까지, 2분.

### S19. 워커 (43분부터 45분까지, 2분)

**한 문장 정의:** 워커는 배정받은 작업을 실제 수행하는 실행 주체이며, 읽기 전용 조사나 파일 수정 등 맡은 일에 따라 권한과 작업 범위가 달라진다.

**상세 설명:**
- 워커는 읽기 전용일 수도 있고 쓰기를 맡을 수도 있다. 같은 파일을 여러 작성자가 동시에 고치면 충돌 위험이 있으므로 쓰기 담당과 경로를 명확히 한다.
- 워커는 세션 안에서 도는 실행일 수도, 별도 프로세스일 수도 있다. 제품마다 다르다.
- 워커의 보고는 자기 보고다. 완료 여부는 검증 단계가 판단한다(S24).

**구체 예시:** 실습 폴더에서 보고서 작성을 맡은 실행 주체가 워커다. 작업 지시에 쓰기 허용 경로 output/revised/를 적고, tickets.csv는 쓰지 말라고 적는다. 범위를 벗어난 쓰기가 생기면 그 워커의 결과부터 확인한다.

**헷갈리는 지점:** 워커와 서브에이전트는 다르다. 워커는 배정받은 일을 수행하는 역할이고, 서브에이전트는 상위와 하위의 위임 관계를 뜻한다. 하위 에이전트가 워커 역할을 할 수 있으며 둘 다 읽기 전용일 수 있다(S20).

**화면 구성:** 워커 상자 하나. 입력 칸에는 작업 지시 파일 목록, 출력 칸에는 쓰기 허용 경로를 적는다. 점선으로 권한 경계를 긋고, 경계 밖에 tickets.csv를 "쓰기 금지"로 표시한다.

**확인 질문과 모범 답안:** 워커가 "보고서 저장 완료"라고 했다. 쓰기 주체였으니 결과가 옳다고 말해도 되는가? 아니다. 쓰기 주체라는 것은 책임 범위를 말할 뿐이며, 결과 확인은 검증 단계에서 한다.

**시간:** 43분부터 45분까지, 2분.

### S20. 서브에이전트 (45분부터 47분까지, 2분)

**한 문장 정의:** 서브에이전트는 상위 작업이 맡긴 하위 작업을 별도의 입력 맥락에서 수행하고 결과를 상위에 돌려주는 하위 실행이며, 읽기 전용일 수도 있고 쓰기 권한을 가질 수도 있다.

**상세 설명:**
- 서브에이전트는 자기 입력과 지시를 따로 받는다. 상위 대화 전체를 자동으로 공유하지 않는 경우가 많다. 공유 범위는 제품마다 다르다.
- 파일을 고치지 않고 읽고 요약하거나 검색만 하는 읽기 전용 역할도 가능하다.
- 서브에이전트가 있다고 독립 검토가 보장되지는 않는다. 같은 모델과 지침을 쓰면 편향을 공유할 수 있다.

**구체 예시:** 모호한 행 목록만 따로 읽고 이유를 정리하는 하위 실행을 맡긴다. 이 서브에이전트는 파일을 쓰지 않는 읽기 전용 역할이다. 결과 목록을 상위 보고서에 붙인다. 워크샵 실습에서는 서브에이전트를 쓰지 않는다.

**헷갈리는 지점:** 서브에이전트와 워커는 다르다(S19). 서브에이전트와 오케스트레이션도 다르다. 오케스트레이션은 배정 방식이고, 서브에이전트는 실행 단위다(S7).

**화면 구성:** 상위 작업 상자에서 하위 실행 상자로 입력을 보내고, 하위 상자에서 결과가 상위로 돌아온다. 하위 상자 안에 "쓰기 권한 없음"을 표시한다.

**확인 질문과 모범 답안:** 서브에이전트가 "검토 완료"라고 보고했다. 독립 검토가 이루어졌는가? 아니다. 같은 모델과 맥락을 공유하면 독립성이 약하다. 검증 기준을 별도로 확인해야 한다.

**시간:** 45분부터 47분까지, 2분.

### 단계 E: 흐름과 검증

### S21. 워크플로우 (47분부터 51분까지, 4분)

**한 문장 정의:** 워크플로우는 입력, 단계, 각 단계의 산출물, 다음 단계로 넘어가는 조건을 정해 둔 작업 흐름이다.

**상세 설명:**
- 핵심은 순서와 전환 조건이다. 단계만 나열할 수도 있지만 실제 운영에 쓰려면 다음 단계로 넘어갈 조건과 실패 시 돌아갈 곳을 명확히 하는 편이 좋다.
- 단계마다 산출물이 있어야 다음 단계가 확인할 수 있다.
- 워크플로우 자체는 자동으로 실행되지 않아도 된다. 사람이 단계를 따라도 워크플로우다.

**구체 예시:** AI교양 제작 흐름(2.3)에서 전환 조건은 사용자의 최종 확정이다. 확정 전에는 삽화 단계가 열리지 않는다. 확정 뒤에는 삽화 생성, 원문과 이미지 보존, 비공개 초안, 재열람 검증이 순서대로 이어진다.

**헷갈리는 지점:** 워크플로우는 자동화와 다르다. 자동화는 그중 일부를 조건이 맞으면 시작하는 장치다(S22). 워크플로우는 하네스와도 다르다. 하네스는 이 단계를 돌리고 검증하는 틀이다(S29에서 업무용 하네스로 다시 본다).

**화면 구성:** 가로 네 칸 흐름도. 칸은 원문 보존 v01, 수정과 확인, 사용자 최종 확정, 삽화와 보존과 비공개 초안과 재열람 검증이다. 세 번째 칸에는 다이아몬드 모양 전환 조건을 그리고 "사람이 결정"이라고 적는다.

**확인 질문과 모범 답안:** 사용자가 최종 확정 메시지를 보내지 않았는데 모델이 삽화를 만들어도 되는가? 아니다. 최종 확정은 사람이 정하는 전환 조건이다.

**시간:** 47분부터 51분까지, 4분.

### S22. 자동화 (51분부터 53분까지, 2분)

**한 문장 정의:** 자동화는 시간, 이벤트, 또는 앞 단계의 결과 같은 조건이 충족되면 정해진 작업을 사람이 다시 시작하지 않아도 실행하도록 만든 장치다.

**상세 설명:**
- 자동화는 시작 조건과 실행할 작업을 정한다. 실행되었다는 사실이 결과의 옳음을 보장하지는 않는다.
- 실행 기록과 실패 기록을 남겨야 나중에 확인할 수 있다.
- 사람이 결정하는 단계는 자동화 대상에서 빼는 것이 보통이다.

**구체 예시:** AI교양 흐름에서 "사용자 최종 확정 메시지"는 이벤트다. 이 이벤트 뒤에 삽화 생성, 보존, 비공개 초안 작성, 재열람 검증을 잇도록 설계할 수 있다. 공개 발행은 조건에 넣지 않는다. 이 설명은 교육용이며, 이번 작업으로 자동화를 설정하거나 실행하지 않았다.

**헷갈리는 지점:** 자동화와 워크플로우는 다르다(S21). 자동화와 자동 기억도 다르다. 자동 기억은 저장과 불러오기의 문제이고, 자동화는 실행 시작의 문제다(S17).

**화면 구성:** 트리거 상자(최종 확정 메시지)에서 작업 묶음 상자(삽화, 보존, 초안, 재열람)로 화살표가 간다. 끝에 기록 상자(실행 로그, 실패 기록)를 둔다. 사람이 결정하는 확정 단계는 점선 상자로 자동화 바깥에 그린다.

**확인 질문과 모범 답안:** 매주 월요일 자동 실행되는 보고서 작업이 있다. 실행 기록에 성공이 찍혔다. 보고서가 맞다고 해도 되는가? 아니다. 성공 기록은 실행이 끝났다는 것만 보여 준다. 검증이 따로 필요하다.

**시간:** 51분부터 53분까지, 2분.

### S23. 완료 보고 (53분부터 55분까지, 2분)

**한 문장 정의:** 완료 보고는 작업자가 "끝났다"고 말한 기록이며, 무엇을 했고 무엇을 확인했다고 주장하는지를 담지만 그 자체가 검증 증거는 아니다.

**상세 설명:**
- 완료 보고에는 무엇을 했는지, 어디에 저장했는지, 무엇을 확인했다고 주장하는지가 들어간다.
- 완료 보고는 증거와 함께 있어야 쓸모가 있다. 증거는 파일 경로, 실행 출력, 재열람 결과다.
- 실패나 미확인 사항도 적어야 한다. 전부 완료라고만 쓰면 인계가 어렵다.

**구체 예시:** 워커가 "보고서 저장 및 건수 검증 완료"라고 보고했다. output/revised/report.md는 있지만, 보고서의 건수 42는 원본 행 수 40과도 고유 티켓 수 38과도 맞지 않는다. 보고는 완료지만 검증은 실패다.

**헷갈리는 지점:** 완료 보고는 주장이고, 검증은 기준에 따른 확인이다(S24). 실행 도구의 done은 실행 종료 상태의 증거일 수 있지만, 산출물이 요구 조건을 모두 만족한다는 증거와는 다르다.

**화면 구성:** 보고 카드 샘플. 상태 완료, 산출물 output/revised/report.md, 확인 항목 건수 검증 완료, 미확인 없음. 카드 옆 대조 칸에 파일 존재는 예, 건수 일치는 아니오로 표시한다.

**확인 질문과 모범 답안:** 완료 보고에 "테스트 통과"라고 적혀 있다. 검증으로 인정해도 되는가? 테스트 명령과 실행 출력을 함께 봐야 한다. 문장만 있으면 자기 보고다.

**시간:** 53분부터 55분까지, 2분.

### S24. 검증 (55분부터 58분까지, 3분)

**한 문장 정의:** 검증은 미리 정한 기준에 따라 산출물, 숫자, 인용, 파일 상태, 실행 결과를 작업자의 말과 독립된 방법으로 확인해 판단하는 과정이다.

**상세 설명:**
- 기준은 작업 전에 정한다. 기준 없이 "좋아 보임"으로 판단하면 검증이 아니다.
- 결정적 검증은 같은 입력에 같은 결과가 나오는 도구로 한다. 행 수 세기, 파일 존재 확인, 테스트 실행이 여기에 해당한다. 두 번째 모델이 필요하지 않다.
- 의미 판단이 필요한 항목은 사람이 읽고 확인하거나 별도 체크 항목으로 남긴다.

**구체 예시:** 체크리스트에 "모호 행이 빠짐없이 목록에 있는가"를 넣는다. 도구로 tickets.csv에서 빈 칸이나 형식이 다른 날짜가 있는 행 번호를 뽑아 보고서 목록과 대조한다. 빠진 행이 있으면 실패로 기록한다.

**헷갈리는 지점:** 같은 작업자가 자기 결과를 다시 읽는 것은 약한 점검이다. 리뷰는 판단이고, 검증은 기준에 따른 확인이다. 둘을 함께 쓸 수 있지만 서로 대신하지는 못한다.

**화면 구성:** 목록 형식으로 항목, 확인 방법, 결과 기록 칸을 나란히 둔다. 예를 들어 항목은 건수 일치, 확인 방법은 행 수 세기 명령, 결과는 "원본 40, 고유 38, 보고서 42, 실패"다.

**확인 질문과 모범 답안:** 보고서 건수가 원본 행 수와 맞는다. 검증이 끝났는가? 아니다. 고유 티켓 수, 모호 행 목록, 근거 인용도 확인해야 한다. 한 항목 통과가 전체 통과는 아니다.

**시간:** 55분부터 58분까지, 3분.

### 단계 F: 실행 위치와 개입 방식

### S25. 로컬 실행 (58분부터 60분까지, 2분)

**한 문장 정의:** 로컬 실행은 도구와 프로세스가 사용자의 컴퓨터에서 돌고, 파일 접근과 명령이 그 기기 안에서 일어나는 방식이며, 모델 추론의 위치와는 별도로 말해야 한다.

**상세 설명:**
- 로컬은 파일 도구와 명령이 내 기기에서 돈다는 뜻이다. 모델 추론의 위치는 따로 확인한다.
- 로컬 실행이어도 모델을 호출하려면 인터넷과 계정이 필요할 수 있다. 실습에서 외부 조회는 없지만 모델 서비스 연결은 필요하다.
- 로컬 실행이 안전하다는 뜻은 아니다. 권한과 범위 설정이 여전히 필요하다.

**구체 예시:** 실습 폴더의 tickets.csv를 읽고 output/baseline/report.md를 쓰는 도구 실행은 참가자의 노트북에서 일어난다. 모델에게 보내는 요청과 응답은 모델 서비스를 거친다.

**헷갈리는 지점:** "로컬에서 돌렸다"는 말이 모델도 기기 안에서 돌았다는 뜻은 아니다. 로컬 실행은 실행 위치이고, 리모트 컨트롤은 개입 방식이다(S27).

**화면 구성:** 노트북 상자 안에 도구, 파일, 실습 폴더를 넣는다. 상자 밖에 모델 추론 서비스 상자를 두고 점선 화살표로 잇는다. 화살표 위에 "요청과 응답"이라고 적는다.

**확인 질문과 모범 답안:** 노트북에서 파일을 읽고 쓰는 도구를 실행했다. 모델 추론도 노트북에서 일어났는가? 그렇다고 단정할 수 없다. 도구 실행 위치와 모델 추론 위치는 따로 확인해야 한다.

**시간:** 58분부터 60분까지, 2분.

### S26. 클라우드 실행 (60분부터 62분까지, 2분)

**한 문장 정의:** 클라우드 실행은 도구, 워커, 또는 모델 추론 중 일부나 전부가 사용자 기기가 아닌 외부 서버 환경에서 돌아가는 방식이며, 어느 구성 요소가 클라우드인지 함께 말해야 한다.

**상세 설명:**
- 클라우드는 실행 환경의 위치다. 파일 환경이 서버에 있을 수도 있고, 모델 추론만 서버에 있을 수도 있다.
- 공유 환경, 접근 권한, 상태 저장 위치가 로컬과 다를 수 있다. 공유 범위는 제품 설정에 따르며, 모든 파일이 전역으로 공유된다고 가정하지 않는다.
- 클라우드 서비스가 항상 정상이라고 가정하지 않는다.

**구체 예시:** 사용자가 제공한 Grokbot 설명에는 공유 클라우드 환경이 나온다(S30). 이번 워크샵은 그 사실을 독립적으로 확인하지 않았다. 참가자의 실습 폴더는 로컬이다.

**헷갈리는 지점:** 모델만 클라우드에서 돌고 파일 도구는 로컬일 수 있다. 이를 "클라우드 작업"이라고 한 단어로 묶으면 위치가 흐려진다. 클라우드 실행과 리모트 컨트롤도 다르다(S27).

**화면 구성:** 두 열. 왼쪽 "내 기기" 상자에 도구와 파일, 오른쪽 "외부 서버" 상자에 모델 추론을 넣는다. 구성 요소마다 라벨을 따로 붙이고, 아래에 "클라우드라는 말만으로는 어느 부분인지 알 수 없다"고 적는다.

**확인 질문과 모범 답안:** 모델 추론은 클라우드에서 하고 파일은 내 노트북에서 고친다. 클라우드 실행인가? 구성 요소별로 답해야 한다. 추론은 클라우드, 파일 도구는 로컬이라고 나눠 말한다.

**시간:** 60분부터 62분까지, 2분.

### S27. 리모트 컨트롤 (62분부터 65분까지, 3분)

**한 문장 정의:** 리모트 컨트롤은 실제 실행을 원래 환경에서 계속하면서, 다른 화면이나 기기에서 그 세션을 보고 지시하거나 중단 신호를 보내는 접근 및 개입 방식이다.

**상세 설명:**
- 리모트 컨트롤은 실행 위치가 아니라 조작 방식이다. 실행은 원래 기기나 서버에서 돈다.
- 연결되어 있다는 것과 앱에서 같은 세션이 보인다는 것은 다르다. 서버 연결 상태만으로 가시성을 주장하지 않는다.
- 같은 워커를 보고 조종하는 것이지 두 번째 쓰기 주체가 아니다. 앱에서 파일을 따로 고치는 작업자가 생기면 충돌이 난다.
- 실습에 필수가 아니다. 권한 우회 옵션도 필수 설정으로 가르치지 않는다. 이 장의 3분 안에서 60초 이내의 시연 또는 정적 화면으로 설명한다. 시연과 녹화 자료는 아직 제작하지 않았다.

**구체 예시:** 노트북에서 실행 중인 워커 세션에 휴대폰 앱으로 중단 신호를 보낸다. 실행은 노트북에서 멈추고, 파일도 노트북에 그대로 남는다. 강사 시연에서는 로그의 활성 표시와 세션 링크를 확인하는 순서로 보여 준다.

**헷갈리는 지점:** 리모트 컨트롤은 클라우드 실행과 다르다(S26). 실행 위치와 개입 방식은 별개의 축이다. ACP 같은 다른 연결 경로와도 다르며, 한 경로로 연결되었다고 다른 경로의 앱 가시성이 보장되지는 않는다.

**화면 구성:** 노트북 상자 안에 워커와 파일, 앱 상자 안에 같은 세션 화면과 중단 버튼을 둔다. 두 상자 사이에 양방향 화살표로 "보기와 지시"를 적는다. 파일 상자는 노트북 안에만 두고, "앱은 두 번째 쓰기 주체가 아니다"라고 주석을 단다.

**확인 질문과 모범 답안:** 휴대폰 앱에서 세션이 보이고, 앱에서 수정을 지시하자 파일이 바뀌었다. 실행 위치는 어디인가? 워커가 원래 돌고 있던 노트북이다. 앱은 보고 지시하는 화면이다.

**시간:** 62분부터 65분까지, 3분.

## 4. 구조와 사례 (65분부터 75분까지)

### S28. OpenClaw 아키텍처 (65분부터 69분까지, 4분)

**한 문장 정의:** OpenClaw는 이 워크샵의 설명용 사례이며, 디스코드나 컨트롤 UI의 요청을 게이트웨이와 세션이 받고, 코디네이터가 직접 처리할지 워커에 맡길지 판단하는 로컬 구조다.

**상세 설명:**
- 흐름은 요청, 게이트웨이와 세션, 코디네이터, 직접 도구 또는 원격 워커, 프로젝트 파일과 테스트, 부모의 독립 검증, 답장 순서다.
- 위임 기준은 코디네이터가 읽고 적용하는 운영 지침이다. 자동으로 강제되는 라우터가 아니다.
- 원격 앱은 같은 워커를 보고 개입하는 화면이다. 두 번째 쓰기 주체가 아니다.
- 참가자 노트북에 OpenClaw를 설치하지 않는다. 실시간 상태는 이번 작업에서 확인하지 않았다.

**구체 예시:** 디스코드에서 "보고서 검증해 줘"라는 요청이 오면 게이트웨이가 세션을 만들고 코디네이터가 직접 확인할지 워커에 맡길지 정한다. 워커가 파일을 고치면 부모가 테스트와 파일 상태를 독립적으로 확인한 뒤 답장한다.

**헷갈리는 지점:** 게이트웨이는 채널과 세션을 관리하는 층이고, 코디네이터는 맡길지 판단하는 주체다. 워커는 배정된 실제 작업을 수행하며 쓰기를 맡은 경우 작성 책임을 진다(S19). 원격 앱은 리모트 컨트롤 화면이다(S27).

**화면 구성:** ASCII 다이어그램 한 장.

```
[Discord / Control UI]  요청과 대화
        |
        v
[Gateway / 세션]  채널과 세션 상태 (S18)
        |
        v
[OpenClaw 코디네이터]  직접 처리 또는 위임 판단 (S7)
        |
        +--> [직접 도구]  조회, 단순 편집 (S8, S25)
        |
        +--> [Codex 또는 Claude 원격 워커]  쓰기 책임 (S19)
                 |
                 v
        [프로젝트 파일 / 테스트]
                 |
                 v
        [부모 독립 검증]  산출물과 프로세스 확인 (S24)
                 |
                 v
        [답장]  요약과 로그 경로

[원격 앱]  같은 워커를 보고 개입 (S27), 두 번째 쓰기 주체 아님
```

**확인 질문과 모범 답안:** 원격 앱에서 같은 세션이 보인다. 워커가 두 개인가? 아니다. 보기와 개입이 늘었을 뿐 쓰기 주체는 하나다.

**시간:** 65분부터 69분까지, 4분.

### S29. AI교양 좁은 업무 하네스 (69분부터 72분까지, 3분)

**한 문장 정의:** AI교양 제작 흐름은 워크플로우이고, 그 흐름을 반복 가능하게 만드는 규칙, 컨텍스트, 도구, 상태, 검증을 묶으면 좁은 업무용 하네스로 설명할 수 있다. 자동 전환을 강제하는 별도 상태 머신이 구현되었다는 뜻은 아니다.

**상세 설명:**
- 규칙은 원문 보존과 버전 관리, 확정 문장 불변, 비공개 초안의 범위다.
- 컨텍스트는 해당 글, 수정 이력, 관련 근거를 명시적으로 넣는 것이다.
- 도구는 파일 저장, 이미지 생성, 초안 작성이다. 상태는 현재 버전, 확정 여부, 단계별 결과, 초안 식별자다. 검증은 저장본 대조와 초안 재열람이다.

**구체 예시:** 완료 기록을 보면 확정 문장을 저장본과 대조해 일치를 확인했고, 삽화를 볼트에 복사한 뒤 해시가 일치함을 확인했다. 비공개 초안은 재열람해 본문, 대표 이미지, 이미지 순서, 카테고리를 확인했고 공개 발행은 하지 않았다. 이 기록은 설명용 인용이다.

**헷갈리는 지점:** 워크플로우와 하네스는 같은 말이 아니다(S21, S6). 단계만 보면 워크플로우이고, 그 단계를 실행하고 검증하는 장치까지 포함하면 업무용 하네스다.

**화면 구성:** 가운데 네 단계 흐름, 주변에 규칙, 컨텍스트, 도구, 상태, 검증 다섯 칸. 각 칸에 AI교양 예시를 한 줄씩 적는다. 주석은 "단계만 보면 워크플로우, 실행을 받치는 장치까지 보면 업무용 하네스"다.

**확인 질문과 모범 답안:** 이 흐름에서 자동으로 실행되는 것과 사람이 결정하는 것을 나누면? 사용자의 최종 확정은 사람이 결정하고, 저장과 초안 작성과 재열람은 정해진 절차로 실행되며, 공개 발행은 범위 밖이다.

**시간:** 69분부터 72분까지, 3분.

### S30. Grokbot 패턴 비교 (72분부터 75분까지, 3분)

**한 문장 정의:** Grokbot은 사용자가 제공한 설명 사례이며, 역할별 봇 네 개, 공유 클라우드 환경, 커넥터와 루틴이라는 패턴을 OpenClaw의 로컬 구조와 비교하는 틀로만 쓴다. 제품 사양이나 벤치마크가 아니다.

**상세 설명:**
- 비교 축은 네 가지다. 누가 책임지는가, 작업이 어디서 실행되는가, 상태가 어디에 남는가, 사람이 어디서 개입하는가.
- Grokbot 쪽 내용은 사용자가 설명한 대로 옮긴 것이며 독립적으로 검증하지 않았다.
- 클라우드가 항상 동작한다거나 모든 파일이 전역으로 공유된다거나 구글 브라우저 로그인 제한이 있다고 말하지 않는다.

**구체 예시:** 책임 축에서 Grokbot 설명은 역할별 봇이 각자 책임을 나눈다고 쓴다. OpenClaw 사례는 코디네이터가 판단하고 워커가 쓰며 부모가 검증한다. 같은 질문도 책임이 어디 있는지에 따라 다르게 보인다.

**헷갈리는 지점:** 봇이 네 개라고 에이전트가 많이 필요한 것은 아니다. 하네스는 단일 도구와 컨텍스트, 검증만으로도 성립할 수 있다. 공유 클라우드는 실행 위치의 한 형태이고 개입 방식과는 별개다(S26, S27).

**화면 구성:** 네 축 목록. 각 축마다 Grokbot 설명과 OpenClaw 사례를 한 줄씩 쓴다. 표가 아니라 목록이다. 맨 아래에 "사용자 설명, 미검증"이라고 적는다.

**확인 질문과 모범 답안:** 우리 팀 도구를 고른다면 네 축 중 무엇이 가장 중요한가? 정답은 없다. 청중의 답을 받고, 각 축의 책임과 상태 위치를 확인하는 질문으로 마무리한다.

**시간:** 72분부터 75분까지, 3분.

참가자 실습은 Claude Code 또는 Codex 하나로 한다. 준비 3분을 포함해 30분이다. OpenClaw, Remote, 플러그인, MCP, API 키는 필요하지 않다.

### S32. 실습 준비 (85분부터 88분까지, 3분)

**한 문장 정의:** 실습 준비는 참가자별 독립 실습 폴더를 만들고, 선택한 도구가 그 폴더의 파일을 읽고 쓸 수 있는지 확인하는 단계다.

**상세 설명:**
- 실습 폴더 하나를 만들고 tickets.csv, output/baseline/, output/revised/ 빈 폴더를 둔다.
- rules.md, task.md, schema.md, checklist.md, handoff.md는 실습 직전에 배포하는 빈 틀이며 이번 작업에서는 만들지 않았다.
- 확인할 것은 세 가지다. 폴더 안 파일을 읽는다. output에 파일을 쓴다. 폴더 밖에는 쓰지 않는다.

**구체 예시:** "tickets.csv의 첫 두 줄을 읽어 보여 줘"라고 요청한다. 응답이 실제 파일 내용과 맞으면 읽기 확인이 된 것이다.

**헷갈리는 지점:** 설치 점검과 실습을 섞지 않는다. 설치가 안 된 참가자는 쉬는 시간에 정리한다.

**화면 구성:** 폴더 구조 목록과 확인 칸 세 개(읽기, 쓰기, 폴더 밖 쓰기 없음).

**확인 질문과 모범 답안:** 도구가 말한 내용이 실제 tickets.csv와 다르다. 어떻게 판단하나? 파일을 직접 열어 대조하고, 불일치하면 도구의 읽기 기록과 경로를 확인한다.

**시간:** 85분부터 88분까지, 3분.

### S33. 1차 실습: 기준선 보고서 (88분부터 93분까지, 5분)

**한 문장 정의:** 기준선 실습은 규칙 파일 없이 한 줄 요청만으로 보고서를 만들고, output/baseline/report.md에 따로 보존하는 단계다.

**상세 설명:**
- 요청은 "이 CSV로 주간 고객 문의 보고서를 써 줘" 한 줄이다. 규칙 파일을 읽으라고 지시하지 않는다.
- 결과는 덮어쓰지 않고 보존한다. 나중에 비교하기 위해서다.
- 저장 뒤 참가자는 원본 행 수와 고유 티켓 수를 직접 세어 메모만 한다. 보고서는 아직 고치지 않는다.

**구체 예시:** 기준선 보고서에 "총 40건"이라고 적혀 있다. 참가자는 원본 행 수 40과 고유 티켓 수 38을 메모하고, 보고서가 어느 숫자를 쓰는지 기록한다.

**헷갈리는 지점:** 기준선은 실패 예시가 아니다. 지시가 적을 때 결과가 어떤 모습인지 보는 기준점이다. 우연히 좋은 결과가 나올 수도 있으며, 그것도 기록한다.

**화면 구성:** 체크 항목 다섯 개와 빈 메모 칸. 항목은 건수 구분, 모호 행 목록, 근거 인용, 날짜 처리, 추정 값 유무다.

**확인 질문과 모범 답안:** 기준선 결과가 틀린 것 같지만 문제가 없어 보인다. 어떻게 기록하나? 확인한 항목과 확인하지 못한 항목을 나눠 적는다. 이것이 자기 보고와 검증을 나누는 연습이다.

**시간:** 88분부터 93분까지, 5분.

### S34. 2차 실습: 규칙, 절차, 출력 형식 추가 (93분부터 103분까지, 10분)

**한 문장 정의:** 보강 실습은 같은 데이터와 완료 기준을 두고, 규칙, 작업 절차, 출력 형식, 체크리스트를 명시적으로 읽히는 방식으로 같은 작업을 반복 가능하게 만든 뒤 output/revised/report.md를 새로 만드는 단계다.

**상세 설명:**
- rules.md에는 날짜가 두 가지 이상으로 읽히면 변환하지 않는다, 빈 칸은 추정하지 않는다, 중복 ticket_id는 행을 합치지 않는다는 규칙을 쓴다.
- task.md에는 행 수 세기, 고유 티켓 수 세기, 모호 행 목록, 보고서 쓰기, 체크리스트 대조 순서를 쓴다.
- schema.md에는 보고서 섹션 순서를 쓰고, 건수는 원본 행 수와 고유 티켓 수를 따로 적는 칸을 둔다.
- 프롬프트에는 "rules.md, task.md, schema.md, checklist.md를 먼저 읽고 그 기준대로 작업하고 검증하라"를 명시한다.

**구체 예시:** rules.md의 한 줄은 "날짜가 두 가지 이상으로 읽히면 변환하지 않고 행 식별자와 함께 모호 목록에 적는다"이다. 이 규칙이 있으면 03/04/2026이 임의 변환되지 않는다.

**헷갈리는 지점:** 규칙 파일을 만든다고 자동으로 따르는 것은 아니다. 자동 지침 탐색 여부에 의존하지 않도록 실습에서는 프롬프트에 읽을 파일을 명시하고 실제 도구 결과를 확인한다(S13). 결과가 기준선과 같을 수도 있으며, 그 경우도 기록한다.

**화면 구성:** 세 파일의 빈 틀을 나란히 보여 주고 각각 예시 한 줄을 넣는다. 맨 아래에 프롬프트 한 줄과 저장 경로 두 개를 둔다. 기준선은 output/baseline/, 보강본은 output/revised/다.

**확인 질문과 모범 답안:** 보강본을 저장하다가 baseline 파일을 덮어썼다. 어떻게 복구하나? 기준선 원본이 남아 있는지 확인하고, 두 결과를 분리하는 경로 규칙을 다시 적는다.

**시간:** 93분부터 103분까지, 10분.

### S35. 2차 실습: 검증 체크리스트 실행 (103분부터 110분까지, 7분)

**한 문장 정의:** 검증 실행은 checklist.md의 항목으로 보고서를 확인하고, 각 항목의 통과, 실패, 미확인을 기록하는 단계다. 같은 모델에게 "맞지?"라고 묻는 것으로 대신하지 않는다.

**상세 설명:**
- 원본 행 수와 고유 ticket_id 수를 명령이나 직접 세기로 다시 세고, 보고서 숫자와 대조한다.
- 빈 칸이나 형식이 모호한 행이 모호 목록에 빠짐없이 들어갔는지 확인한다.
- 주요 주장마다 행 식별자(줄 번호와 ticket_id)가 있는지, 보고서에 CSV에 없는 값이 없는지, schema.md 섹션이 모두 있는지 확인한다.

**구체 예시:** 참가자가 tickets.csv에서 빈 칸이 있는 행을 줄 번호와 함께 뽑아, 보고서 모호 목록과 한 줄씩 대조한다. 목록에 없는 행이 하나라도 있으면 실패로 기록한다.

**헷갈리는 지점:** 같은 세션에 "맞지?"라고 다시 묻는 것은 검증이 아니다(S24). 결정적 검사는 세기와 대조로 한다. 두 번째 모델은 필요하지 않다.

**화면 구성:** 항목, 확인 방법, 결과 칸을 목록으로 적는다. 예를 들어 항목은 건수 구분, 확인 방법은 행 수와 고유 ticket_id 세기, 결과는 "원본 40, 고유 38, 보고서 기재 값, 통과 또는 실패"다.

**확인 질문과 모범 답안:** 다섯 항목 중 네 개가 통과했다. 검증된 것인가? 아니다. 한 항목이라도 실패하면 실패로 기록하고, 미확인 항목도 완료로 세지 않는다.

**시간:** 103분부터 110분까지, 7분.

### S36. 2차 실습: 명시적 인계와 두 번째 세션 (110분부터 115분까지, 5분)

**한 문장 정의:** 명시적 인계는 현재 세션의 목적, 완료 기준, 확인된 사실, 미확인 사항, 다음 단계를 handoff.md에 쓰고, 새 세션이 그 파일과 규칙을 명시적으로 읽은 뒤 이어 가는 단계다.

**상세 설명:**
- handoff.md에는 목적, 완료 기준, 확인된 사실과 근거, 미확인 사항, 다음 단계, 참조 파일을 쓴다.
- 새 세션 프롬프트는 "handoff.md, rules.md, task.md를 먼저 읽고 미확인 사항부터 이어서 하라"로 쓴다.
- 새 세션이 이전 대화를 기억한다고 가정하지 않는다. 이 실습은 인계 파일에 적힌 사실과 남은 일에 근거해 이어졌는지 확인한다.
- 새 세션의 결과는 체크리스트로 다시 확인한다. 같은 모델의 새 세션은 독립 평가자가 아니다.
- 마지막 1분은 산출물 위치와 자기 업무에서 같은 틀을 쓸 수 있는 작업 하나를 적는 데 쓴다. 스킬 후보로만 말하고 설치하지 않는다.

**구체 예시:** handoff.md에 "모호 행 7건 중 날짜 규칙 적용 결과 3건 미확인"이라고 적는다. 새 세션이 이 파일을 읽고 세 건부터 확인하면 인계가 된 것이다. 새 세션에 다른 경로로 맥락이 전달됐다고 가정하지 않고 인계 파일을 명시적으로 읽힌다.

**헷갈리는 지점:** 인계 파일은 자동 기억이 아니다(S17). 인계가 되었는지는 새 세션이 읽은 근거를 함께 재진술할 때 확인된다.

**화면 구성:** handoff.md 빈 틀의 여섯 칸(목적, 완료 기준, 확인된 사실, 미확인 사항, 다음 단계, 참조 파일)과 새 세션 프롬프트 한 줄.

**확인 질문과 모범 답안:** 새 세션이 "어제 말씀드린 대로 모호 행은 일곱 건입니다"라고 답했다. 인계가 된 것인가? 확인할 수 없다. handoff.md와 보고서를 열어 일곱 건이 실제로 적혀 있는지 대조해야 한다.

**시간:** 110분부터 115분까지, 5분.

### S37. 질의응답과 정리 (115분부터 120분까지, 5분)

**한 문장 정의:** 질의응답은 참가자의 질문을 받아 용어와 실습 산출물을 다시 확인하는 시간이다.

**상세 설명:**

- 산출물 위치를 다시 말한다. 기준선은 output/baseline/report.md, 보강본은 output/revised/report.md, 인계 파일은 handoff.md다.
- 다음 실행 명령은 없다. 증거는 각자 실습 폴더의 파일과 체크리스트 기록이다.

**구체 예시:** 질문이 없으면 "가장 헷갈렸던 용어 하나와 그 이유"를 묻고, 해당 슬라이드 번호를 보여 준다.

**헷갈리는 지점:** 질의응답에서 제품 기능을 단정하지 않는다. 확인이 필요한 답은 확인 필요라고 말한다.

**화면 구성:** 질문 받기 화면, 용어 목록 요약, 산출물 위치 한 장.

**확인 질문과 모범 답안:** "이 방식이면 항상 정확한가요?" 아니다. 기준과 검증으로 점검 가능해질 뿐이며 결과가 보장되지는 않는다.

**시간:** 115분부터 120분까지, 5분.

- 에이전트는 실제 응답 횟수로 판정하지 않으며, 기본 하네스와 업무용 구성의 보강을 구분했다.
- 읽기 전용 워커, 세션 이력과 현재 컨텍스트, MCP 인증과 실제 권한, 문서 지시와 기술적 제한을 구분했다.
- 3분 리모트 컨트롤 장의 시연 예시는 60초 이내로 제한했다.
