# OpenClaw 하네스 워크샵 슬라이드 내용 기획 v03

이 문서는 실제 슬라이드나 PDF가 아니라 슬라이드별 내용 정의서다. 각 슬라이드마다 제목, 핵심 메시지, 실제로 들어갈 내용, 화면 구성, 시간, 진행 방법과 실습 연결을 적었다. 앞선 워크샵 노트 `openclaw-harness-workshop-v01.md`는 그대로 두었고, 이 문서는 별도 버전이다.

## 0. 전체 설계 요약

- 총 슬라이드는 휴식과 실습 정리를 포함해 26장이다.
- 시간표 합계는 120분이다. 앞부분 70분, 쉬는 시간 10분, 뒷부분 40분으로 나뉜다.
- 쉬는 시간은 10분이다.
- 참가자 실습은 33분이다. 실습 단계는 준비 4분, 1차 느슨한 요청 10분, 2차 규칙 보강 12분, 3차 인계와 두 번째 세션 7분이다.
- 질의응답은 5분이다.
- 앞부분에서 용어 설명에 40분을 쓴다. 용어를 먼저 맞추고 나서 구조와 사례로 넘어간다.
- 핵심 실습은 OpenClaw 없이 Claude Code 또는 Codex만으로 진행한다. OpenClaw는 설명용 사례로만 보여 준다.

### 학습 목표

1. 모델, 에이전트, 런타임, 하네스, 도구, 스킬, 플러그인, MCP 커넥터, 세션, 워커, 서브에이전트, 워크플로, 자동화, 검증을 같은 뜻으로 쓸 수 있다. 다만 이 용어들은 도구마다 쓰임이 다르므로 워크샵 작업 정의를 따른다.
2. 같은 지시라도 지시문만 주는 것과 환경, 컨텍스트, 도구, 검증을 갖춘 루프로 주는 것이 결과를 어떻게 바꾸는지 설명할 수 있다.
3. 자기 보고와 독립 검증을 구분하고, 검증 체크리스트를 직접 만들 수 있다.
4. 로컬, 클라우드, 원격 제어를 서로 다른 축으로 구분해 설명할 수 있다.
5. 반복 가능한 작업 파일 묶음(rules.md, task.md, 출력 스키마, 검증 체크리스트, handoff.md)을 만들고, 두 번째 세션이 그것만 읽고 이어서 작업하게 할 수 있다.

### 청중 가정

- 기술 배경이 섞여 있다. 개발자, 운영 담당, 기획, 기록 담당이 함께 듣는다고 가정한다.
- 참가자 각자 Claude Code 또는 Codex가 설치되어 있고 로그인되어 있으며, 로컬 실습 폴더를 읽고 쓸 수 있다고 가정한다.
- 일반 브라우저 채팅에서 로컬 폴더 접근 기능이 있다고 가정하지 않는다. 이번 실습 경로는 폴더 읽기와 쓰기가 가능한 Claude Code 또는 Codex 환경으로 한정한다. 다른 화면의 동일 기능 지원 여부는 사전 점검 대상이다.
- 핵심 실습에 OpenClaw 설치, Remote 설정, 플러그인 설치, MCP 서버 연결, API 키 발급을 요구하지 않는다.
- 파이썬은 선택 사항이다. 실습 자체는 파이썬 없이 가능해야 한다.

### 두 가지 동등한 도구 경로

- 경로 A는 Claude Code다. 실습 폴더를 열고, 프롬프트에서 rules.md를 명시적으로 포함해 실행한다.
- 경로 B는 Codex다. 같은 폴더에서 같은 프롬프트와 같은 파일을 쓴다.
- 두 경로는 같은 과제를 같은 파일로 수행한다. 어느 쪽이 더 좋은 결과를 낸다는 주장은 하지 않는다.
- 두 도구 모두 프로젝트 지침 파일을 자동으로 읽을 수 있다. 대표적인 지침 파일은 Codex의 AGENTS.md와 Claude Code의 CLAUDE.md다. 최신 Claude Code는 조건에 따라 AGENTS.md도 읽으므로 제품 전용 확장자처럼 가르치지 않는다. 다만 이 이름은 도구마다 다르고 모든 도구에 보편적이지 않다. 실습에서는 공통 규칙을 rules.md에 두고 프롬프트에 명시해 포함하므로 자동 탐색에 의존하지 않는다.

### 공통 실습 데이터

- 합성 고객 문의 티켓 CSV 한 개를 사용한다. 실제 고객 정보는 없다.
- 열은 티켓 번호, 접수 일시, 채널, 분류, 요약, 우선순위, 담당자, 상태, 처리 일시다.
- 의도적으로 모호한 행을 넣는다. 예를 들면 분류가 비어 있는 행, 날짜 형식이 섞인 행, 같은 티켓 번호가 두 번 나오는 행, 우선순위가 "긴급!!"과 "high"로 섞인 행, 담당자가 없는 행을 둔다.
- 완료 기준은 다음과 같다. 전체 건수가 CSV 행 수와 맞아야 한다. 모호한 행은 따로 목록으로 적어야 한다. 근거 없이 값을 추정하면 안 된다. 주요 주장마다 원본 행 식별자를 인용해야 한다. 중복 티켓 번호만으로 행을 구분하지 않는다. 중복을 포함한 원본 행 수와 고유 티켓 수를 분리해 보고하고, 날짜가 모호하면 임의 변환하지 않는다.
- 실습에서는 메일 발송, 외부 데이터 조회, 공개 배포를 하지 않는다. Claude Code 또는 Codex의 모델 서비스 연결에 필요한 인터넷과 계정 이용은 별개다. 모든 도구 실행은 참가자별 독립 실습 폴더 안에서만 한다.

## 1. 개요 구간 (00분에서 10분)

### S1. 워크샵 목표와 진행 방식 (00분에서 03분)

- 핵심 메시지: 오늘은 AI 도구를 잘 쓰는 요령보다 같은 용어와 같은 작업 틀을 맞추는 시간이다.
- 실제 내용: 학습 목표 다섯 개를 짧게 보여 준다. 진행 순서는 도입 10분, 용어 40분, 구조와 사례 20분, 휴식 10분, 실습 33분, 실습 정리 2분, 질의응답 5분이다.
- 화면: 목표 다섯 줄과 시간 막대 하나.
- 진행: 참가자에게 "오늘 끝나면 어떤 질문에 답할 수 있어야 하는지"를 한 번 물어본다.
- 실습 연결: 없음.

### S2. 청중 가정과 두 가지 실습 경로 (03분에서 05분)

- 핵심 메시지: 실습은 이미 쓰는 Claude Code 또는 Codex 하나면 충분하다.
- 실제 내용: 가정 네 가지를 보여 준다. 설치와 로그인이 되어 있다. 로컬 폴더를 읽고 쓸 수 있다. 실습에 OpenClaw, Remote, 플러그인, MCP, API 키가 필요하지 않다. 파이썬은 선택 사항이다. 경로 A와 경로 B를 나란히 보여 준다.
- 화면: 두 열로 된 경로 비교 화면. 각 열에 실행 위치, 공통 규칙 파일 포함 방식, 지침 파일 관례를 적는다.
- 진행: 설치가 안 된 참가자는 쉬는 시간 전에 옆 사람과 짝을 맺는다. 설치를 실습 중에 하지 않는다고 미리 말한다.
- 실습 연결: 실습 준비 단계(S20)의 사전 점검으로 이어진다.

## 2. 반복 예시와 용어 지도 (05분에서 10분)

### S3. 반복 예시: 고객 문의 티켓 보고서 (05분에서 10분)

- 핵심 메시지: 모든 용어를 같은 예시로 설명한다. 예시는 티켓 CSV를 읽고 주간 보고서를 쓰는 작업이다.
- 실제 내용: 입력은 CSV 한 개다. 출력은 Markdown 보고서 한 개다. 보고서는 건수 요약, 분류별 주요 문의, 우선순위 높은 건, 모호한 행 목록, 근거 행 인용으로 구성한다. 이 예시가 이후 모든 용어 슬라이드에 등장한다.
- 화면: CSV 일곱 행 샘플과 보고서 목차 초안. 모호한 행 세 개에 표시를 한다.
- 진행: 참가자에게 이 보고서를 사람이 쓰면 무엇을 확인할지 두 가지만 말해 달라고 한다. 답은 나중에 검증 체크리스트와 연결한다.
- 실습 연결: 실습의 데이터와 완료 기준(S20, S21)과 같은 것이다.

## 3. 용어 블록 (10분에서 50분, 40분)

각 개념 슬라이드는 같은 순서를 따른다. 운영상 정의, 익숙한 구체 예시, 헷갈리는 이웃 용어와의 구분, 빠른 확인 질문 한 개다. 워크샵 작업 정의임을 슬라이드마다 밝힌다.

### S4. 모델과 에이전트 (10분에서 14분)

- 핵심 메시지: 모델은 입력을 받아 추론하고 응답이나 도구 호출 요청을 생성하는 엔진이고, 에이전트는 그 모델이 도구를 골라 쓰며 여러 단계를 도는 실행 구조다.
- 운영상 정의: 도구 호출 요청을 만들 수 있어도 모델 자체가 파일을 직접 읽는 것은 아니다. 런타임이 도구를 실행하고 그 결과를 모델에 돌려준다. 에이전트는 모델에 목표를 주고 도구 호출과 결과 확인을 반복하게 만든 구성이다. 워크샵에서는 모델 자체를 에이전트라고 부르지 않는다.
- 구체 예시: 티켓 보고서를 쓸 때, 모델은 문장을 쓰는 부분이다. 에이전트는 CSV를 열고, 행을 세고, 빈 칸을 찾고, 초안을 쓰고, 다시 확인하는 순환을 맡는 부분이다.
- 헷갈리는 이웃: 같은 모델을 쓰더라도 도구와 지시가 다르면 다른 에이전트처럼 행동한다. "모델을 바꿨다"와 "에이전트를 바꿨다"는 다른 말이다.
- 빠른 확인: CSV를 직접 열어 행을 세는 것은 모델만의 일인가, 도구가 있는 실행 구조의 일인가? 답은 도구가 있는 실행 구조다.
- 실습 연결: 실습에서 같은 모델 위에서 도구와 파일을 붙였을 때 결과가 달라지는지 본다.

### S5. 런타임: 모델의 요청을 실제 실행으로 이어주는 층 (14분에서 17분)

- 핵심 메시지: 이 교육에서 에이전트 런타임은 모델 호출, 도구 실행, 결과 전달과 다음 단계 진행을 실제로 구동하는 소프트웨어 실행 계층을 뜻한다.
- 운영상 정의: 모델은 도구를 쓰라는 요청을 만들고, 런타임은 등록된 도구와 실행 권한을 확인해 실행을 연결한다. 도구의 성공 결과나 오류를 받아 모델에 돌려주고, 다음 모델 호출이나 종료를 이어간다. 구체적인 담당 범위는 제품 구조에 따라 다를 수 있다.
- 구체 예시: 모델이 tickets.csv를 읽도록 요청한다. 런타임이 파일 읽기 도구를 호출한다. 도구가 파일 내용 또는 파일 없음 오류를 반환한다. 런타임이 그 결과를 모델 입력에 반영하고 모델이 다음 행동을 판단하도록 진행한다.
- 화면: 모델의 호출 요청, 런타임의 도구 연결, 파일 읽기 도구, 실행 결과, 모델의 다음 판단을 순서도로 그린다. 실행 결과에서 다음 판단으로 돌아가는 루프를 강조한다.
- 헷갈리는 이웃: 모델은 판단과 생성의 엔진, 런타임은 그 요청을 실제 실행으로 이어주는 계층, 하네스는 지침과 컨텍스트 구성, 런타임, 도구, 상태 관리와 검증 절차를 묶은 더 넓은 작업 틀로 구분한다. 런타임과 하네스의 명명 경계는 생태계마다 다를 수 있다.
- 다른 용례: Python 런타임이나 Node.js 런타임은 프로그램 실행 환경을 가리키는 별도 용례다. 에이전트 런타임이 내부에서 이런 언어 런타임을 사용할 수 있지만 둘을 같은 층으로 보지 않는다.
- 빠른 확인: 모델이 파일 읽기를 요청했는데 실제 파일 접근이 차단됐다면 모델의 답변 내용만 볼 것인가? 아니다. 런타임과 도구의 권한, 실행 위치, 오류 기록을 함께 확인한다.
- 실습 연결: Claude Code나 Codex에서 도구 요청과 성공 또는 오류 결과가 이어지는 모습을 보고, 모델의 요청과 실제 실행을 구분한다. 참가자가 별도 런타임을 설치하는 실습은 아니다.

### S6. 하네스와 오케스트레이션 (17분에서 20분)

- 핵심 메시지: 하네스는 모델을 감싸는 작업 환경 전체다. 오케스트레이션은 여러 실행 단위의 순서와 배분을 정하는 일이다.
- 운영상 정의: 하네스는 컨텍스트, 도구, 실행 위치, 상태 저장, 검증 단계를 합친 틀이다. 오케스트레이션은 누가 언제 무엇을 맡는지 조율하는 층이다.
- 구체 예시: 보고서 작업에서 하네스는 작업 폴더, 규칙 파일, 출력 형식, 검증 체크리스트를 제공한다. 오케스트레이션은 "먼저 분류 집계, 다음에 모호한 행 목록, 마지막에 검토" 순서를 정하는 것이다.
- 헷갈리는 이웃: 하네스와 오케스트레이션을 같은 말로 쓰는 경우가 많다. 하네스는 틀이고, 오케스트레이션은 그 틀 안에서 일을 나누는 방식이다. 하네스의 범위는 제품마다 다르다. 이 워크샵에서는 작업 환경과 실행 루프를 묶어 부르고, 오케스트레이션은 그 안의 순서와 역할 배정으로 구분한다. 여러 에이전트가 필수라는 뜻은 아니다.
- 빠른 확인: 검증 체크리스트를 파일로 두는 것은 하네스 요소인가 오케스트레이션 요소인가? 답은 하네스 요소다.
- 실습 연결: 실습 2차에서 체크리스트와 출력 스키마를 만드는 것이 하네스를 만드는 일이다.

### S7. 도구와 스킬 (20분에서 24분)

- 핵심 메시지: 도구는 모델이 실제로 호출하는 기능이고, 스킬은 그 기능을 언제 어떤 순서로 쓸지 적은 절차 묶음이다.
- 운영상 정의: 도구는 파일 읽기, 쓰기, 명령 실행처럼 호출 가능한 기능이다. 스킬은 절차 설명과 필요한 자원을 묶은 재사용 단위다. 스킬은 도구가 아니며 도구를 쓰는 방법을 적은 것이다.
- 구체 예시: 파일 읽기는 도구다. "CSV를 열면 먼저 헤더를 확인하고, 날짜 형식을 통일하고, 빈 칸을 목록화한다"는 절차는 스킬 후보다.
- 헷갈리는 이웃: 스킬을 도구라고 부르면 능력을 과장하게 된다. 스킬은 재사용 절차와 자원 묶음이다. 스크립트를 포함할 수 있지만 실제 실행은 도구와 런타임이 맡는다. 워크샵에서는 절차를 rules.md와 task.md로 먼저 쓰고, 나중에 스킬로 바꿀 수 있다고만 말한다.
- 빠른 확인: "날짜를 ISO 형식으로 바꾼다"는 도구인가 절차인가? 답은 절차다. 실제 변환 기능을 호출하면 도구다.
- 실습 연결: rules.md와 task.md가 스킬이 될 수 있는 절차 후보다. 실습에서는 스킬을 설치하지 않는다.

### S8. 플러그인과 MCP 커넥터 (24분에서 27분)

- 핵심 메시지: 플러그인은 기능과 지침을 배포하는 패키지다. 커넥터는 외부 서비스와의 연결이고, MCP는 도구와 자원을 연결하는 통신 규약이다. 연결과 포장, 프로토콜을 구분한다.
- 운영상 정의: 프로토콜은 통신 규칙이다. 포장은 여러 기능과 지침을 한 번에 설치하는 묶음이다. 커넥터는 외부 서비스나 데이터에 접근하는 연결 지점이다. 워크샵에서는 이 구분을 기준으로 쓴다.
- 구체 예시: MCP 서버가 CSV 파일을 읽는 도구를 제공하면, 그 도구는 MCP를 통해 모델에 노출된다. 여러 도구와 지침을 묶은 것이 플러그인이다.
- 헷갈리는 이웃: MCP라고 하면 모든 도구가 MCP라고 오해하기 쉽다. 또 플러그인이 있으면 기능이 자동으로 보장된다고 생각하기 쉽다. 둘 다 아니다. 실제 사용 가능 여부는 설치와 권한을 확인해야 한다.
- 빠른 확인: MCP는 도구인가 프로토콜인가? 답은 프로토콜이다. 그 위에서 도구가 노출된다.
- 실습 연결: 핵심 실습에서는 플러그인과 MCP를 쓰지 않는다. 연결 개념만 설명하고 실습 폴더의 파일 도구로 대체한다.

### S9. 프롬프트, 컨텍스트, 메모리 (27분에서 31분)

- 핵심 메시지: 프롬프트는 모델에 주는 지시나 질문이고, 컨텍스트는 모델이 그 순간 볼 수 있는 전체 입력이며, 메모리는 여러 세션에 걸쳐 남기는 저장물이다.
- 운영상 정의: 프롬프트는 이번 요청일 수도 있고 지속 지침일 수도 있다. 컨텍스트는 그 순간 모델 입력에 실제로 포함된 지시, 파일 내용, 도구 결과, 이전 대화다. 파일이 디스크에 있다는 것만으로 컨텍스트에 포함되지는 않는다. 토큰은 입력과 출력을 세는 단위이며, 컨텍스트 창은 한 번에 다룰 수 있는 범위다. 요약과 압축 과정에서 세부 내용이 빠질 수 있다. 메모리는 나중에 다시 불러올 수 있도록 파일이나 저장소에 남긴 정보다.
- 구체 예시: "이 CSV로 보고서 써줘"는 프롬프트다. 같은 세션에서 CSV 내용과 규칙 파일이 함께 들어가면 컨텍스트다. 다음 날 handoff.md를 읽고 이어가는 것은 파일 기반 메모리 역할이다.
- 헷갈리는 이웃: 메모리라는 말은 도구가 자동으로 기억했다는 뜻으로 오해되기 쉽다. 워크샵에서는 자동 기억을 주장하지 않는다. 두 번째 세션이 이어 가는 것은 파일을 명시적으로 읽었기 때문이다.
- 빠른 확인: 새 세션에 어제 대화가 자동으로 전달되는가? 답은 제품의 세션 복원이나 메모리 기능에 따라 다르므로 가정하면 안 된다는 것이다. 이 실습에서는 인계 파일을 명시적으로 읽게 한다.
- 실습 연결: 3차 실습에서 두 번째 세션이 handoff.md를 명시적으로 읽는다. 자동 기억이 아님을 확인하는 실습이다.

### S10. 세션, 워커, 서브에이전트 (31분에서 35분)

- 핵심 메시지: 세션은 작업이 이어지는 단위이고, 워커는 실제로 파일을 고치고 명령을 실행하는 실행 주체이며, 서브에이전트는 한 작업 안에서 떨어져 나간 하위 실행이다.
- 운영상 정의: 세션은 대화와 상태가 묶인 실행 단위다. 워커는 쓰기를 하는 주체다. 서브에이전트는 상위 작업이 맡긴 하위 작업을 따로 수행하는 실행이다.
- 구체 예시: 보고서 작업의 대화와 상태를 담는 그릇이 세션이고, 그 안에서 실제 실행을 맡는 주체를 워커라고 부른다. 둘은 이 사례에서 대응할 수 있지만 같은 개념은 아니다. 모호한 행만 따로 검토하라고 띄운 하위 실행이 서브에이전트다. 세션 기록을 남긴 것이 나중에 이어갈 수 있는 세션이다.
- 헷갈리는 이웃: 세션과 워커를 같은 것으로 보기 쉽다. 같은 세션을 여러 화면에서 볼 수 있어도 쓰기 주체는 하나여야 한다.
- 빠른 확인: 두 화면이 같은 세션을 보고 있으면 워커가 둘인가? 답은 아니다. 쓰기 주체가 둘이면 충돌이 생긴다.
- 실습 연결: 실습에서는 서브에이전트를 쓰지 않는다. 사람이 역할을 바꿔 가며 기획자, 실행자, 검토자 순서로 맡는다. 이것은 독립 검토자를 증명하는 것이 아니다.

### S11. 워크플로와 자동화 (35분에서 38분)

- 핵심 메시지: 워크플로는 정해진 단계의 순서이고, 자동화는 사람이 누르지 않아도 조건에 따라 실행되게 만든 것이다.
- 운영상 정의: 워크플로는 단계와 입력, 출력이 정해진 작업 흐름이다. 자동화는 시간이나 이벤트 조건으로 워크플로를 시작하는 장치다. 자동화가 있어도 워크플로가 없으면 같은 실수가 자동으로 반복된다.
- 구체 예시: 매주 월요일 CSV를 읽어 보고서를 쓰는 순서는 워크플로다. 그 순서를 매주 자동으로 시작하게 하는 것이 자동화다.
- 헷갈리는 이웃: 자동화된 것은 검증된 것이라고 생각하기 쉽다. 자동화는 실행을 시작하고 이어가는 장치이며, 환경 장애가 있으면 실행 자체도 실패할 수 있다. 결과의 옳음은 별도로 검증해야 한다.
- 빠른 확인: 매주 자동 실행되지만 검증 단계가 없는 보고서는 자동화인가 워크플로인가? 답은 자동화이면서 워크플로가 불완전한 상태다.
- 실습 연결: 실습 1차와 2차에서 같은 작업을 반복 가능한 순서로 쓰는 것이 워크플로를 만드는 일이다. 자동 실행은 실습 범위가 아니다.

### S12. 검증과 자기 보고 (38분에서 42분)

- 핵심 메시지: 자기 보고는 작업자가 "끝났다"고 말하는 것이고, 검증은 별도 기준으로 결과를 확인하는 것이다. 둘은 같지 않다.
- 운영상 정의: 자기 보고는 작업자의 말이다. 독립 검증은 정해진 기준에 따라 산출물, 숫자, 인용, 파일 상태를 확인하는 행위다. 검증 기준은 작업 전에 정해 둔다.
- 구체 예시: 보고서가 "총 42건입니다"라고 말해도 CSV 행 수가 40이면 검증에서 실패한다. 체크리스트로 행 수를 세는 것이 독립 검증이다.
- 헷갈리는 이웃: 같은 도구가 다시 확인해 주는 것도 검증이라고 생각하기 쉽다. 같은 작업자가 다시 읽었다는 말만으로 독립 검증이 되지는 않는다. 다만 도구로 건수를 다시 세거나 정해진 테스트를 실행한 증거는 유효한 검증 수단이다. 검증에 항상 두 번째 모델이 필요한 것은 아니다. 이번 워크샵에서는 독립 검토자라고 주장하지 않는다.
- 빠른 확인: "작업자가 테스트 통과라고 했다"는 검증인가 자기 보고인가? 답은 자기 보고다. 테스트를 직접 실행한 출력을 봐야 검증이다.
- 실습 연결: 2차 실습에서 검증 체크리스트를 만든다. 3차 실습에서 두 번째 세션이 이 체크리스트로 이전 결과를 확인한다.

### S13. 로컬, 클라우드, 원격 제어 축 (42분에서 46분)

- 핵심 메시지: 로컬, 클라우드, 원격 제어는 서로 다른 축이다. 어디서 실행되는지, 누가 실행을 맡는지, 사람이 어디서 보고 개입하는지를 나눠서 봐야 한다.
- 운영상 정의: 로컬과 클라우드는 무엇의 실행 위치인지 함께 말해야 한다. 파일 도구와 명령은 내 컴퓨터에서 실행하면서 모델 추론은 클라우드 API를 이용할 수 있다. 작업 도구의 위치와 모델 추론의 위치를 별도 축으로 그린다. 원격 제어는 실행은 한 곳에서 되고 화면과 개입은 다른 곳에서 하는 방식을 뜻한다.
- 구체 예시: 내 노트북에서 CSV를 읽는 것은 로컬 실행이다. 같은 작업을 외부 서버에서 돌리는 것은 클라우드 실행이다. 노트북 실행을 휴대폰 앱에서 보고 멈추는 것은 원격 제어다.
- 헷갈리는 이웃: 원격 제어를 클라우드로 오해하기 쉽다. 원격 제어는 실행 위치가 아니라 개입 방식이다. 또 클라우드라고 항상 잘 동작하거나 모든 파일이 공유된다는 뜻도 아니다.
- 빠른 확인: 노트북에서 실행되고 휴대폰에서 보기만 하는 작업은 클라우드인가? 답은 아니다. 로컬 실행에 원격 제어가 붙은 것이다.
- 실습 연결: 핵심 실습은 로컬 실습 폴더에서만 한다. 원격 제어는 강사 시연으로만 본다(S17).

### S14. 용어 빠른 점검 (46분에서 50분)

- 핵심 메시지: 방금 배운 핵심 용어를 짧은 질문으로 다시 맞춘다.
- 실제 내용: 대표 네 문항을 보여 준다. 예를 들면 "도구 호출 요청을 실제 실행으로 이어주는 층은 무엇인가", "CSV 행 수를 세는 것은 도구인가 모델인가", "두 번째 세션이 어제 내용을 아는 이유는 무엇인가", "자동화된 보고서가 맞다는 보장은 무엇인가"다. 각 문항 옆에 짧은 정답을 숨겨 두고 강사가 공개한다.
- 화면: 질문 네 개와 정답 공개 영역.
- 진행: 손을 들거나 채팅으로 답하게 하고, 틀린 항목은 한 문장으로 다시 정리한다. 점검은 평가가 아니라 어휘 맞추기다.
- 실습 연결: 실습 중 용어가 헷갈리면 이 화면으로 돌아온다.

## 4. 루프 시연과 구조 (50분에서 70분)

### S15. 지시문만 줄 때와 환경 루프로 줄 때 (50분에서 57분)

- 핵심 메시지: 같은 모델에서도 환경, 컨텍스트, 도구, 검증 루프를 어떻게 구성하는지에 따라 작업의 재현성과 점검 가능성이 달라질 수 있다. 결과가 반드시 좋아진다고 미리 결론 내리지는 않는다.
- 실제 내용: 두 줄 비교를 보여 준다. 왼쪽은 지시문만 준 경우다. 오른쪽은 실습 폴더, rules.md, 출력 스키마, 체크리스트, 실행 후 검증 단계를 갖춘 경우다. 오른쪽은 실행, 검증, 수정, 다시 검증의 루프를 돈다.
- 화면: 두 열 흐름도. 왼쪽은 한 줄 화살표다. 오른쪽은 원형 루프다. 두 열 모두 같은 CSV 예시를 쓴다.
- 진행: 지시문만 준 결과에서 빠진 것, 즉 모호한 행 목록, 근거 인용, 건수 합계를 참가자와 같이 찾는다. 프롬프트를 더 잘 쓰는 것이 아니라 틀을 바꾸는 것이 핵심이라고 정리한다.
- 실습 연결: 실습 1차는 왼쪽, 실습 2차는 오른쪽 방식이다.

### S16. OpenClaw 시스템 개요 (57분에서 61분)

- 핵심 메시지: OpenClaw는 이 워크샵의 설명용 사례다. 디스코드나 컨트롤 UI에서 받은 요청을 게이트웨이와 세션이 받고, 코디네이터가 직접 처리할지 워커에 맡길지 판단한다.
- 실제 내용: 흐름은 디스코드 또는 컨트롤 UI, 게이트웨이와 세션, OpenClaw 코디네이터, 직접 도구 또는 Codex나 Claude 원격 워커, 프로젝트 파일과 테스트, 부모의 독립 검증, 답장 순서다. 위임 기준은 코디네이터가 읽고 적용하는 운영 지침이며 별도 강제 자동 라우터가 아니라고 명시한다.
- 화면: ASCII 구조 다이어그램 한 장. 원격 앱은 같은 워커를 보고 개입하는 화면이며 두 번째 쓰기 주체가 아니라는 표시를 붙인다.
- 진행: 실습 실행은 OpenClaw 없이 한다고 다시 말한다. 참가자 노트북에 OpenClaw를 설치하지 않는다.
- 실습 연결: 없음. 설명용이다.

### S17. 원격 제어 시연 (61분에서 66분)

- 핵심 메시지: 원격 제어는 실행과 화면을 나누는 방식이다. 연결되어 있다는 것과 앱에서 실제로 보인다는 것은 다르다.
- 실제 내용: 강사가 5분 안팎으로 보여 준다. 실행 후 로그에서 활성 여부와 세션 링크를 확인하고, 앱에서 같은 세션이 보이는지 확인하는 순서다. 연결 상태만으로 완료라고 하지 않는다고 강조한다.
- 화면: 강사 시연용 세션과 녹화 한 편을 사전에 준비할 계획이다. 아직 녹화 산출물은 만들지 않았다. 실시간 시연이 막히면 준비된 녹화를 재생하거나 정적 구조도로 설명한다. 녹화 재생이라는 사실을 화면에 밝힌다.
- 진행: 참가자는 따라 하지 않는다. 원격 제어는 참가자 필수 요건이 아니라고 명시한다. 권한 우회 옵션도 필수 설정으로 가르치지 않는다.
- 실습 연결: 없음. 실습은 로컬 폴더 기준이다.

### S18. Grokbot 참조 사례와 비교 틀 (66분에서 70분)

- 핵심 메시지: Grokbot은 사용자가 제공한 설명 사례다. 역할별 봇 네 개, 공유 클라우드 환경, 커넥터와 루틴이라는 패턴을 OpenClaw의 로컬 게이트웨이와 공식 코딩 원격 구성과 비교한다. 이 비교는 패턴 비교이며 제품 벤치마크가 아니다.
- 실제 내용: 비교 축은 네 가지다. 누가 책임지는가, 작업이 어디서 실행되는가, 상태가 어디에 남는가, 사람이 어디서 개입하는가다. Grokbot 쪽에 대해서는 사용자 설명을 그대로 옮기고 독립 검증하지 않았다고 밝힌다. 클라우드가 항상 동작한다거나 모든 파일이 전역으로 공유된다거나 구글 브라우저 로그인 제한이 있다는 주장은 하지 않는다.
- 화면: 네 축 비교 목록. 두 사례가 각 축에서 어떻게 다른지 한 줄씩 적는다. 표 대신 목록을 쓴다.
- 진행: 청중에게 "우리 팀 도구라면 어느 축이 가장 중요한가"를 묻는다.
- 실습 연결: 없음. 설명용이다.

## 5. 쉬는 시간 (70분에서 80분)

### S19. 쉬는 시간 (70분에서 80분)

- 핵심 메시지: 10분 휴식이다. 실습 전에 설치와 로그인을 확인한다.
- 실제 내용: 실습 폴더를 만들 위치와 Claude Code 또는 Codex 실행 확인 방법을 한 장에 적는다.
- 화면: 단순 안내 화면과 남은 시간 표시.
- 진행: 설치가 안 된 참가자는 이 시간에 짝과 함께 점검한다. 설치를 강사가 대신하지 않는다.

## 6. 실습 구간 (80분에서 115분, 준비와 실습 33분 및 정리 2분)

### S20. 실습 준비: 독립 폴더와 파일 배치 (80분에서 84분)

- 핵심 메시지: 모든 도구 실행은 참가자별 독립 실습 폴더 안에서만 한다.
- 실제 내용: 실습 폴더 하나를 만든다. 그 안에 입력 tickets.csv, 출력 폴더 output/, rules.md, task.md, schema.md, checklist.md, handoff.md의 빈 틀을 둔다. 입력 데이터와 틀은 추후 배포할 실습 자료이며 아직 제작하지 않았다. 폴더 밖 쓰기는 하지 않는다. 실행 범위 지침은 기술적 샌드박스와 다르며, 도구 권한을 무조건 우회하는 설정은 실습 요건이 아니다. 설치나 API 키 설정은 없다.
- 화면: 폴더 구조 목록과 확인 체크 세 개: 실행 도구가 열린다, 폴더 안 파일을 읽는다, 폴더 밖 쓰기를 하지 않는다.
- 진행: 경로 A와 경로 B 중 하나를 고른다. 같은 파일을 쓴다는 것을 다시 확인한다.
- 실습 연결: 이후 모든 실습 단계의 출발점이다.

### S21. 1차 실습: 느슨한 한 줄 요청 (84분에서 94분)

- 핵심 메시지: 지시문만 주고 결과를 본 뒤, 무엇이 빠졌는지 찾는다.
- 실제 내용: 참가자는 "이 CSV로 주간 고객 문의 보고서를 써 줘"라는 한 줄만 입력한다. 결과를 output/report-v01.md로 보존한 뒤 다섯 항목을 체크한다. 건수가 맞는가, 모호한 행을 목록으로 적었는가, 근거 행을 인용했는가, 날짜 형식을 어떻게 처리했는가, 추정한 값이 있는가다. 체크 결과를 짧게 적는다.
- 화면: 체크리스트 다섯 항목과 빈 기록란.
- 진행: 10분 중 7분은 실행과 체크, 3분은 짝과 결과 비교다. 정답을 주지 않고 빠진 항목을 참가자가 찾게 한다.
- 실습 연결: 2차 실습의 출발점이다.

### S22. 2차 실습: 규칙, 작업 지시, 출력 스키마 추가 (94분에서 100분)

- 핵심 메시지: 같은 데이터와 같은 완료 기준으로, 틀을 추가해 같은 작업을 반복 가능하게 만든다.
- 실제 내용: 미리 배포할 빈 틀에서 참가자가 rules.md, task.md, schema.md 세 파일의 핵심 항목을 채운다. rules.md에는 날짜 정규화, 빈 칸 처리, 추정 금지, 모호 행 기록 규칙을 쓴다. task.md에는 단계별 작업 순서를 쓴다. schema.md에는 보고서 섹션 순서와 항목을 쓴다. 재실행 결과는 output/report-v02.md에 저장해 1차 결과를 보존한다. 프롬프트에는 "rules.md, task.md, schema.md, checklist.md를 먼저 읽고, 그 기준대로 작업하고 검증한다"라고 명시한다.
- 화면: 세 파일의 빈 틀과 예시 한 줄씩.
- 진행: 참가자가 직접 쓴다. 강사는 규칙이 추정을 허용하는지 같은 질문을 던진다.
- 실습 연결: S23의 체크리스트와 3차 실습의 handoff.md로 이어진다.

### S23. 2차 실습: 검증 체크리스트와 완료 기준 (100분에서 106분)

- 핵심 메시지: 완료 기준은 작업 전에 정하고, 검증은 체크리스트로 한다. 작업자의 "완료" 말은 증거가 아니다.
- 실제 내용: 체크리스트 예시는 다음과 같다. 원본 행 수와 고유 티켓 수를 나눠 셌는가. 모호한 행이 빠짐없이 목록에 있는가. 주요 주장마다 원본 행 식별자가 있는가. 보고서에 CSV에 없는 값이 없는가. 출력 스키마 섹션이 모두 있는가. 참가자는 이 중 세 항목 이상을 직접 확인해 본다.
- 화면: 체크리스트 다섯 항목과 확인 칸.
- 진행: 실행자와 검토자 역할을 사람이 번갈아 맡는다. 실행자가 만든 보고서를 같은 사람이 검토자 자세로 체크하게 한다. 이것은 독립 검토자 증명이 아니라 역할 연습이라고 말한다.
- 실습 연결: 3차 실습에서 두 번째 세션이 이 체크리스트를 쓴다.

### S24. 3차 실습: 인계와 두 번째 세션 (106분에서 113분)

- 핵심 메시지: 두 번째 세션은 handoff.md를 명시적으로 읽어야 이어진다. 자동 기억은 가정하지 않는다.
- 실제 내용: 2차 수정과 확인이 끝난 뒤 기존 세션에서 handoff.md를 쓴다. 작업 실행이 끝난 것을 확인하고 새 세션을 연다. 적을 내용은 목적, 완료 기준, 확인된 사실, 미확인 사항, 다음 단계, 참조 파일이다. 새 세션을 열고, 프롬프트에 "handoff.md, rules.md, task.md를 먼저 읽고 미확인 사항부터 이어서 하라"라고 쓴다. 그 뒤 체크리스트로 결과를 확인한다.
- 화면: handoff.md 빈 틀과 새 세션 프롬프트 한 줄.
- 진행: 새 세션의 자동 기억 여부를 단정하지 않고, 인계 파일을 읽은 내용에서 확인된 사실과 남은 일을 근거와 함께 재진술하게 한다. 같은 모델의 새 세션은 맥락 인계 연습이지 완전히 독립적인 평가자가 아니다.
- 실습 연결: S9의 메모리 구분과 직접 연결된다.

### S25. 실습 정리와 재사용 방향 (113분에서 115분)

- 핵심 메시지: 이 절차는 나중에 스킬로 바꿀 수 있지만, 오늘은 설치하지 않는다.
- 실제 내용: 반복된 절차를 스킬 후보로 적는 방법을 보여 준다. 스킬로 만들려면 입력, 출력, 절차, 검증 기준을 분리한다는 점만 말한다. 스킬 설치와 공유 경로는 다루지 않는다.
- 화면: 실습 산출물인 규칙, 작업 절차, 출력 형식, 체크리스트, 인계 파일과 보고서, 스킬 후보 목록 한 장.
- 진행: 각자 자신의 업무에서 같은 틀을 쓸 수 있는 작업 하나를 적는다.
- 실습 연결: 실습 후 과제로 넘긴다.

## 7. 질의응답과 마무리 (115분에서 120분)

### S26. 질의응답과 마무리 (115분에서 120분)

- 핵심 메시지: 질문을 받고, 오늘 쓴 용어와 파일을 다시 확인한다.
- 실제 내용: 질의응답 5분 이상을 확보한다. 마무리로 실습 산출물인 규칙, 작업 절차, 출력 형식, 체크리스트, 인계 파일과 보고서의 위치를 말한다. 다음 실행 명령은 없다. 오늘 실습의 증거는 각자 폴더 안 파일과 체크리스트 기록이다.
- 화면: 질문 받기 화면과 용어 목록 요약.
- 진행: 질문이 없으면 "가장 헷갈렸던 용어 하나"를 물어본다.
- 실습 연결: 실습 후 각자 다음 작업 하나를 정하도록 남긴다.

## 8. 번호와 시간 확인

- 슬라이드는 S1부터 S26까지 26장이다. S19 휴식과 S25 실습 정리도 번호에 포함했다.
- 시간은 다음과 같다. 개요 10분, 용어 40분, 루프와 구조 20분을 합친 앞부분 70분이 있다. 그다음 쉬는 시간 10분이 있다. 마지막으로 실습 준비와 실습 33분, 실습 정리 2분, 질의응답 5분으로 뒷부분 40분이 있다. 70분과 10분과 40분을 더하면 120분이다.
- 준비를 포함한 실습 시간은 33분이며 준비 4분을 제외한 과제 실행과 점검은 29분이다. 실습 정리 2분은 별도다.
- 질의응답은 5분이다. 기준인 5분 이상을 만족한다.

## 9. 확인하지 않은 항목과 주의

- 이 문서는 내용 정의서다. 실제 슬라이드, PDF, 실습 파일은 만들지 않았다.
- 부모가 Codex AGENTS.md와 Claude Code 지침 파일의 공식 문서를 열어 대조했다. 참가자별 버전과 지침 탐색 동작을 직접 시험한 것은 아니다. 실습은 rules.md를 프롬프트에 명시하는 방식으로 설계했다.
- 원격 제어 시연은 당일 실시간 연결을 확인하지 않은 상태에서 쓴 계획이다. 실시간이 막히면 녹화로 대체한다.
- Grokbot 설명은 사용자가 제공한 내용이며 이번 작업에서 독립 검증하지 않았다.
- 작성 담당은 기존 Claude Remote 세션만 이어서 사용했다. 참가자용 OpenClaw, Remote, 플러그인, MCP 환경을 설치하거나 실습용 서비스를 시작하지 않았다. 부모는 공식 문서 원문을 열람했다.
- 실습 시간과 체크리스트의 효과는 실제 진행 전에는 측정하지 않았다. 결과가 같을 수 있으며, 형식적인 모델 품질 비교 증명으로 제시하지 않는다.
