- 전: 가지 '직접 도구 / 조회, 단순 편집'
  후: 가지 '직접 처리 / 코디네이터가 스스로'

- 전: 가지 '원격 워커 / Codex 또는 Claude'
  후: 가지 '워커에게 위임 / Codex 또는 Claude Code'
  이유: 다른 경로를 행위로 표현
- 전: 코디네이터 상자 '직접 할까, 맡길까'
  후: 그대로 '직접 할까, 맡길까'
  이유: 두 가지와 같은 말로 묻는다
- 전: '프로젝트 / 파일과 테스트'
  후: '작업 결과 / 파일과 테스트 출력'
  이유: 두 가지가 모두 여기로 모인다
- 전: '부모의 / 독립 검증' (흰 상자)
  후: '결과 검증 / 코디네이터가 확인' (코디네이터와 같은 파란 상자)
  이유: 별도의 부모 에이전트는 없다. 같은 코디네이터가 돌아온 결과를 확인한다. 두 상자를 점선과 '같은 코디네이터' 표시로 잇고, 결과가 돌아오는 화살표에 '결과를 돌려받음'을 붙였다
- 전: '원격 앱 / 같은 워커를 보고 개입' (점선, 워커로 가는 선)
  후: '작업 확인 화면 / 진행 확인, 추가 지시' (점선으로 워커 바로 아래에 붙임)
  이유: '원격'이 클라우드 추론처럼 읽히지 않게. 워커의 같은 작업을 보는 화면으로만 그리고, 게이트웨이와 연결된 것처럼 그리지 않는다
- 전: 태그 '세션은 4장', '워커는 4장'
  후: 삭제 (게이트웨이 상자에 '채널과 세션' 유지)
  이유: 9번의 핵심인 경로와 확인 주체에 집중
- 전: aria: '…직접 도구 또는 원격 워커, 파일과 테스트, 부모 검증, 답장'
  후: aria: '…코디네이터가 직접 처리하거나 워커에게 위임, 작업 결과, 같은 코디네이터의 결과 검증, 답장. 작업 확인 화면은 워커가 하는 같은 작업을 본다'
  이유: 화면과 같은 행위자
- 전: 디스코드로 온 "보고서 검증해 줘". 받는 쪽, 맡기는 쪽, 확인하는 쪽은 각각 누구일까?
  후: 디스코드로 온 "보고서 검증해 줘". 누가 받고, 누가 맡기고, 누가 결과를 확인할까?
  이유: 질문을 '누가'로 바꿔 행위자를 묻는다
- 전: 요청을 받고, 맡기고, 따로 확인하는 작업 구조
  후: 요청을 받고, 맡기고, 돌아온 결과를 확인하는 구조
  이유: '따로 확인'은 별도 검증자가 있는 것처럼 읽힌다. 확인하는 쪽은 같은 코디네이터
- 전: 운영 문서를 바탕으로 한 가상 예시 (실시간 상태는 미확인). 위임 기준은 운영 지침일 뿐 자동 라우터가 아니고, 모델 추론 위치는 따로 따짐
  후: 운영 문서 기준의 가상 예시. 두 파란 상자는 같은 코디네이터의 단계. 결과는 테스트와 파일로 확인
  이유: 검증 주체를 짧게 밝힌다. 독립 에이전트가 아니라는 점, 방법과 행위자의 구분, 라우터와 추론 위치 단서는 노트로
- 노트 정정(v10 발췌 앞): v10의 '부모의 독립 검증'은 별도의 부모 에이전트가 아니라, 같은 코디네이터가 워커에게서 돌아온 결과를 확인하는 단계를 가리킨다. 아래 발췌의 해당 줄도 이 표현으로 바꿨다. 테스트 실행, 파일 상태, 원본과의 비교는 코디네이터가 쓰는 확인 방법이자 증거이지 새로운 행위자가 아니다. 독립된 방법이나 독립된 출처로 확인해도 확인하는 쪽은 같은 코디네이터이며, 같은 모델이라면 워커와 같은 오류를 함께 놓칠 수 있다. 코디네이터는 어떤 도구를 쓸지 고를 뿐이고, 도구를 실제로 실행하는 것은 런타임이다. 직접 처리는 코디네이터가 원격 워커에게 맡기지 않고 조회나 간단한 수정을 스스로 하는 경로이고, 워커에게 위임은 Codex나 Claude Code 같은 워커가 작업을 맡는 경로다. 위임 기준은 운영 지침이지 자동 라우터가 아니며, 모델 추론이 어디서 일어나는지는 따로 확인한다. 작업 확인 화면은 워커가 하고 있는 같은 작업과 세션을 보는 화면(예: 워커 쪽 공식 원격 앱)이며, 보고 지시할 뿐 파일을 따로 고치는 두 번째 작업자가 아니다. 게이트웨이와 연결된 화면으로 그리지 않았다.
