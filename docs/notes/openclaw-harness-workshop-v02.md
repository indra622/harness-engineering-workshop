# OpenClaw 하네스 워크샵 강사 노트 v02

이 문서는 슬라이드가 아닌 Markdown 개요와 강사 참고 노트다. 내용은 세 층으로 나눴다. 첫째, 이번 작업에서 로컬 파일을 직접 읽어 확인한 내용이다. 둘째, 워크샵 진행을 위한 권장 교육 계획이다. 셋째, 지금은 확인하지 않았고 당일 다시 확인해야 하는 내용이다.

## 1. 관찰한 로컬 설정

- 직접 읽은 파일은 `reference/remote-delegation.md`, `AGENTS.md`, `SOUL.md`, `USER.md`다.
- 현재 설정은 부모 코디네이터가 설정 파일에서 직접 확인했다. 확인한 값은 gateway mode local, discord 채널 활성, 기본 모델 `openai/gpt-6.1-sol`, 대체 모델 `openai/gpt-6-sol`, `agents.list` 비어 있음이다.
- `agents.list`가 비어 있으므로 독립 전문 에이전트가 구성되어 있다고 가정하지 않는다. 위임은 아래에서 설명할 Codex Remote와 Claude Remote 경로를 기준으로 설명한다.
- runbook에는 2026-09-23과 2026-10-02 테스트에서 Sol과 Astra의 원격 호출, Claude Remote 세션 링크가 확인됐다고 적혀 있다. 이는 과거 기록이다. 오늘 서비스가 정상이라는 증거로 쓰지 않는다.

## 2. 핵심 멘탈 모델

우리 운영에서는 하네스를 모델을 둘러싼 작업 틀 전체로 설명한다. OpenClaw는 상위 조율 하네스이고 Codex와 Claude Code는 각자의 실행 하네스를 가진다. 따라서 하나의 거대한 에이전트보다 여러 하네스를 연결한 구조에 가깝다. 다음 다섯 요소로 설명한다.

- 컨텍스트: 지침 파일과 작업 지시 파일이다. `AGENTS.md`, `SOUL.md`, `USER.md`, 일일 메모리 `memory/YYYY-MM-DD.md`가 여기에 든다. 개인 `MEMORY.md`는 메인 세션에서만 읽는다.
- 도구: 셸, 파일 편집, Codex와 Claude의 원격 CLI, 브라우저 등이다. 도구에 권한이 있다고 해서 작업이 허가된 것은 아니다.
- 실행: 누가 어디서 일하는지다. 코디네이터가 직접 처리하거나, Codex 또는 Claude 워커에 맡긴다.
- 상태: 세션 ID, 로컬 로그 경로, Workboard 카드, automations scratch, 프로젝트 파일과 Git 상태가 상태에 해당한다. 다음 실행과 재연결은 이 상태를 근거로 이어진다.
- 검증: 워커의 보고를 믿지 않고 부모가 산출물, 테스트, 프로세스, Git 상태를 독립적으로 확인하는 단계다.

모델은 생각을 만드는 엔진이고, 하네스는 그 엔진이 안전하게 일하도록 감싸는 틀이다. 이 구분을 처음부터 잡아 두면 이후 실패 사례를 이해하기 쉽다.

## 3. 구조 다이어그램

```
[Discord / Control UI]  요청과 대화
        |
        v
[Gateway / 세션]  채널 연결과 세션 상태
        |
        v
[OpenClaw 코디네이터]  직접 처리할지 위임할지 판단
        |
        +--> [직접 도구]  조회, 단순 편집, 명령 실행
        |
        +--> [Codex Remote 워커]  codex-remote.cjs -> 공식 CLI Remote 서버
        |
        +--> [Claude Remote 워커]  claude --bg --remote-control
                 |
                 v
        [프로젝트 파일 / 테스트 / Git]  쓰기 주체는 하나, 격리 worktree 권장
                 |
                 v
        [부모 독립 검증]  산출물, 테스트, 프로세스, Git 상태 확인
                 |
                 v
        [Discord 답장]  요약과 로컬 로그 경로

[Codex 또는 Claude 앱]  같은 워커 세션을 보고 개입하는 화면이며 두 번째 쓰기 주체가 아니다
```

앱은 워커를 관찰하고 조종하는 화면이다. 앱에서 같은 작업에 지시를 보낼 수 있다. 이와 별개로 같은 파일을 수정하는 두 번째 세션을 띄우지 않는다.

## 4. 용어 구분

- 모델: 추론을 수행하는 엔진이다. 예를 들어 gpt-6.1-sol, gpt-6-astra, Claude 모델이 있다.
- 하네스: 모델을 둘러싼 컨텍스트, 도구, 실행, 상태, 검증 전체다.
- 스킬: 특정 작업의 절차를 담은 지침 묶음이다. 공용 스킬 홈은 `~/.agents/skills`다. 스킬은 모델이 아니다.
- 워커: 실제로 파일을 고치고 명령을 실행하는 실행 주체다. Codex 세션과 Claude 세션이 여기에 해당한다.
- 세션: 작업이 이어지는 단위다. 여러 화면이 같은 세션을 볼 수 있지만 쓰기 주체는 하나여야 한다.
- 네이티브 subagent: 같은 런타임 안에서 띄우는 하위 에이전트다.
- ACP: Agent Client Protocol을 통해 외부 코딩 에이전트와 연결하는 경로다. `sessions_spawn`의 `runtime="acp"`가 그 예다. `sessions_spawn`은 네이티브 하위 에이전트도 지원하므로 호출 자체가 ACP를 뜻하지 않는다. ACP 연결만으로 공식 앱 가시성이 증명되지는 않는다.
- 공식 Remote: `codex-remote.cjs` 또는 `claude --remote-control`을 통한 경로다. 앱에서 같은 세션을 여는지는 따로 확인해야 한다.

## 5. 위임 선택 기준

이 기준은 코디네이터가 읽고 적용하는 현행 Markdown 운영 지침이다. 별도 자동 분류기나 강제 라우터가 구현돼 있다는 뜻은 아니다.

- 대화, 조회, 명확한 단일 파일 수정은 직접 처리한다.
- 여러 파일 구현이나 테스트가 필요한 변경은 Codex `gpt-6.1-sol`에 맡긴다.
- 구조 설계, 얽힌 원인 분석, Sol이 두 차례 해결하지 못한 문제는 `gpt-6-astra`에 맡긴다. 실패한 시도와 근거를 함께 넘긴다.
- 슬라이드나 발표 자료의 주요 내용과 구성을 만들거나 고치는 일은 Claude Code가 구현한다.
- 사용자가 Claude를 지정했거나 독립적인 검토가 유용하면 Claude Code를 쓴다.
- GUI 작업은 공식 Remote 워커의 Computer Use에 맡기고 부모가 범위를 정하고 결과를 검증한다. 2026-10-08 지침에 따른 것이며, Work 모드의 별도 Remote 실행은 아직 실측하지 않았다.

라우팅 선택이 실질적으로 있었던 작업은 직접 처리와 위임 결과를 모두 사례 노트에 기록한다. 관찰하지 않은 시간이나 품질은 추정하지 않고 미측정으로 둔다.

## 6. 앱 가시성: 연결됨과 실제로 보임은 다르다

- 서버가 `connected`를 반환해도 그것은 서버 쪽 상태다. 앱에서 같은 세션이 보이는지는 별도로 확인해야 한다.
- Claude의 `--bg` 실행이 성공했다고 Remote 연결이 보장되지는 않는다. 로그에 `/remote-control is active`가 있고 `https://claude.ai/code/session_...` 링크가 찍혔는지 확인한다. 로그에는 ANSI 제어 문자가 있으므로 요약해서 전달한다.
- Codex 앱에서는 Remote 항목에서 해당 컴퓨터를 고르고 작업 이름의 세션을 연다. 컴퓨터가 보이지 않으면 계정, 워크스페이스, Remote 연결을 먼저 본다.
- 2026-10-02에는 데스크톱 앱과 CLI Remote가 같은 서버 ID를 점유해 409 충돌이 났다. 진행 중인 턴이 없음을 확인한 뒤 앱을 정상 종료하고 CLI Remote를 다시 시작해 해결했다.

## 7. 권한, 감독, 종료 판정

- Codex helper는 `approvalPolicy=never`와 `sandbox=danger-full-access`를 네이티브 API에 전달한다. Claude 실행에는 `--dangerously-skip-permissions`를 쓴다.
- 권한 우회는 작업 허가와 다르다. 배포, 전송, 삭제 권한은 위임 때문에 넓어지지 않는다.
- 워커를 시작한 부모는 그 워커를 끝까지 감독한다. 실행만 하고 끝나면 전달이 아니다.
- `done`이나 `idle` 표시는 완료 증거가 아니다. Codex에서는 `completed` 이벤트의 `turn.status`를, Claude에서는 `done` 상태와 실제 최종 답변을 함께 확인한다.
- `needs input`, `failed`, `stopped`는 성공이 아니다.
- 결과를 받았다고 원격 세션을 자동으로 종료하거나 삭제하지 않는다. 검토용으로 남겨 둘 수 있다.

## 8. 로그, 보드, 자동화, 메모리

- 작업 로그는 `logs/YYYY-MM-DD/<task-name>.log`에 남긴다. Discord에는 상태, 마지막 정상 시각, 실패 지점, 핵심 오류 줄, 복구 시도, 로그 경로만 요약한다.
- 장애가 나면 `memory/YYYY-MM-DD.md`에 사건 노트를 남긴다.
- Workboard 보드 `kresnik-openclaw`는 상태 공유 창구다. 상태는 triage, backlog, todo, ready, running, review, blocked, done을 필요에 따라 사용한다. blocked는 반드시 거치는 순서가 아니다. `done`은 산출물과 검증 증거를 기록한 뒤에만 올린다. 자동 디스패치는 아직 검증되지 않았으므로 쓰지 않는다.
- 자동화 목록은 `openclaw automations list --all`로 보고, scratch는 `openclaw automations scratch <jobId> --set "..."`로 갱신한다.
- `MEMORY.md`는 메인 세션에서만 읽는다. 공유 채널이나 다른 사람이 있는 세션에서는 읽지 않는다.
- 비밀 값, 토큰, 개인 계정 정보는 워크샵 자료와 채팅 로그에 넣지 않는다.

## 9. 쓰기 충돌과 격리

- 한 프로젝트에 쓰기 주체는 하나만 둔다. 같은 프로젝트에 두 워커가 동시에 쓰게 하지 않는다.
- 쓰기 작업은 격리 worktree에서 진행하는 것을 기본으로 한다.
- 이전 worktree에 미커밋 변경이 남아 있으면, 소유 세션과 하위 프로세스 종료, 최종 산출물, 원격 기본 브랜치 반영 여부를 함께 확인한 뒤에만 보존 산출물로 취급한다. 확인되지 않은 변경은 완료로 치지 않는다.
- Cursor Agent 명령 `agent`는 협업 실행기 후보로 등록되어 있다. 다만 공식 Remote 경로와 동등하게 앱 가시성과 작업 검증을 마쳤다고 말하지 않는다.
- pstack은 절차를 보강하는 도구로 쓸 수 있다. 원본 모드와 완전히 호환된다고 보장하지 않는다. 이 평가는 `USER.md`가 인용한 `logs/2026-10-17/pstack-full-validation/report-v01.md`를 근거로 한다. 이번 작업에서 그 보고서는 열어 보지 않았다.

## 10. 실패 사례 3종

사례 1, 연결됨과 앱 가시성의 혼동이다. 서버 상태가 `connected`라서 작업이 앱에 보인다고 판단했다. 실제로는 앱에서 세션 이름을 찾지 못했다. 대응은 앱에서 같은 세션을 열어 보고, 실패하면 Remote 연결과 계정과 워크스페이스를 확인하는 것이다. 보고할 때는 서버 상태와 앱 확인을 따로 적는다.

사례 2, `done`과 검증 완료의 혼동이다. 워커 화면에 `done`이 떠서 완료로 보고했다. 최종 답변에는 테스트 실패가 남아 있었다. 대응은 최종 답변 원문, 산출물 파일, 테스트 명령의 독립 실행 결과, `git status`를 모두 확인한 뒤에만 완료로 쓰는 것이다.

사례 3, 중복 쓰기 주체다. 첫 워커가 응답하지 않아 새 워커를 만들었다. 기존 워커는 살아 있었고 두 워커가 같은 파일을 고쳤다. 대응은 재시도 전에 기존 세션과 프로세스가 살아 있는지 확인하고, 살아 있으면 새로 만들지 않는 것이다. 이미 두 쓰기 주체가 생겼다면 한쪽을 중단하고 변경을 비교한 뒤 하나만 남긴다.

이 세 사례는 교육용 가상 시나리오다. 실제 사고 기록이 아니다.

## 12. 15분 데모 설계

데모는 외부 서비스와 무관한 토이 프로젝트로 한다. 이메일 발송, 공개 배포, 외부 계정 접근은 하지 않는다.

- 준비: 독립 폴더 하나를 만든다. 예를 들어 `~/workshop-demo-toy` 같은 임시 경로를 쓴다. 파일은 `calc.py`와 `test_calc.py` 두 개다. `calc.py`에는 워크샵용 버그 하나를 일부러 넣는다.
- 단계 1: 작업 지시 파일에 목적, 절대 경로, 제약, 완료 조건, 검증 명령을 적는다.
- 단계 2: Remote 연결 상태를 확인하고 앱에서 같은 세션이 보이는지 본다. 명령은 runbook 기준이며 경로와 옵션은 당일 점검이 필요하다.
- 단계 3: 워커가 버그를 고치도록 한다. 부모는 감독만 하고 파일을 직접 고치지 않는다.
- 단계 4: 부모가 `test_calc.py`를 독립적으로 실행한다. 최종 답변만 믿지 않는다.
- 단계 5: `git status`와 diff를 보고 변경 범위가 작업 지시와 같은지 확인한다.
- 단계 6: 할당한 작업 턴과 작업 소유 하위 프로세스가 종료됐는지 확인하고 로그 경로를 남긴다. 검토용 Remote 세션과 연결 서비스는 유지할 수 있다.

당일 실시간 연결이 확인되지 않으면 미리 저장한 로그와 실행 기록을 보여 주는 방식으로 바꾼다. 이때는 실시간 시연이 아니라 기록 재현이라고 분명히 말한다.

- 요청 열 개를 직접 처리, Codex Sol, Astra, Claude, GUI 중에서 분류한다.
- 작업 지시 파일 템플릿을 만든다. 목적, 프로젝트 절대 경로, 제약, 완료 조건, 검증 명령, 쓰기 주체 한 명을 반드시 넣는다.
- 샘플 로그를 읽고 `connected`, `done`, `needs input`, `failed` 중 무엇인지 판정한다.
- 중복 쓰기가 의심되는 상황에서 중단할 지점과 이유를 적는다.
- 워크샵 후 체크리스트를 자기 프로젝트에 맞게 채운다.

## 14. 정리 문장

1. 하네스는 모델을 둘러싼 컨텍스트, 도구, 실행, 상태, 검증의 전체 틀이다.
2. 위임 정책은 코디네이터가 적용하는 운영 지침이며 별도 강제 라우터가 아니다.
3. 앱에서 같은 세션이 보여야 가시성이 확보되며, 서버 연결 상태만으로는 부족하다.
4. 워커의 `done`은 끝이 아니라 부모가 독립적으로 검증할 대상의 시작점이다.
5. 권한 우회는 작업 허가가 아니며, 한 프로젝트의 쓰기 주체는 하나만 둔다.
6. 로그와 실패 기록을 남겨야 다음 실행이 같은 실수를 반복하지 않는다.
